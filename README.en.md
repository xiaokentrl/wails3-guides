A collection of pre-project planning guides, reusable across projects. When starting a new project, **copy the whole `guides/` directory over**, follow the master outline stage by stage, and consult the deep-dive topic guides when you hit deep water.

## Usage Rules

1. **Copy the whole directory**: a new project takes the entire `guides/` directory; the 《title》 references between guides travel with it and never break.
2. **The master outline is the entry point**: answer the "core questions" and record the "acceptance evidence" stage by stage; wherever an item says "→ see the topic guide", the topic guide governs.
3. **Topic guides are the deep water**: the master outline only lists gating questions; each topic's full checklists, root-cause tables and acceptance matrices live in the topic guide.
4. **Cross-project assets follow the same rules**: the component library (`ui/`) accumulates here per the Component Library and Shared Functions guides; `lib-go/` is a Go shared library each new project builds during its own lifetime and is not part of this repository. Copy-migration and backflow discipline is identical.
5. **Release notes**: changes are recorded bilingually in [RELEASES.md](./RELEASES.md); since v1.11.0 each entry uses four sections (**Added / Changed / Fixed / Removed**), with empty sections written as (none); older entries keep their original format and are not rewritten.
6. **Evidence levels**: technical claims fall into four classes — verified against framework source / second-hand from the master outline / common industry practice / legal or compliance clause. Second-hand claims and unverified framework behavior must be marked **to be verified**; legal conclusions belong to counsel, not engineering.
7. **Conditional guides and authority map**: follow the two sections above; a guide enters the must-answer list only when its trigger fires, and cross-cutting topics defer to their master guide.

## Conventions for Adding New Topic Guides

- Filename = topic name, placed in `专题/<theme>/`: existing themes take new guides directly; a new theme opens a new directory. Framework-specific deep pitfalls go into the topic guide; universal principles go into the master outline.
- Structure follows one of three skeletons: **discipline master** (what this guide is → the 10–12 questions AI must answer first → core disciplines → root-cause table → test matrix → AI constraint template → five-stage positioning), **implementation companion** (positioning & hard goals → core design → acceptance checklist → AI constraint template → five-stage positioning; must declare its master guide), or **evidence review** (what this review is → timeline/evidence chain → failure analysis → proposed fix order → acceptance template → boundary statement; must declare its master guide). Section headings may use descriptive variants; the AI constraint template is mandatory, while evidence reviews may omit the five-stage positioning section.
- When adding a guide, update the catalog above; when removing items or changing semantics, check the 《title》 references in other guides.
- Project-specific war stories (which project hit which pitfall) never enter the guides — guides stay generic; lessons go into each project's own docs.
- This README is bilingual: `README.md` (Chinese) and `README.en.md` (English) mirror each other — update both when adding, removing, or changing guides.
