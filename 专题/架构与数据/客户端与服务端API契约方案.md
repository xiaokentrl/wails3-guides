# 客户端与服务端 API 契约方案：通用规划方案

## 这份方案是做什么的

来源：API 评审清单与契约优先/版本化实践（breaking change 目录、废弃与 sunset 标注、错误契约、限流配额、旧客户端兼容窗口）、中文技术方案评审清单的「关键接口清单：接口名称、版本、数据格式、安全要求、变更控制、兼容性策略」。母法方案：《网络与离线弹性技术方案》（超时重试与离线）、《输入数据验证方案》（边界层校验）、《状态码方案》（错误码结构）、《数据模型与数据契约方案》（字段字典与口径）、《登录与权限方案》（认证与会话）、《版本号方案》（多类版本号分治）。

《网络与离线弹性技术方案》管的是「请求怎么发、失败怎么退」，本方案管的是**「接口本身是什么、变了旧客户端怎么办」**：契约定义、版本与兼容、错误语义、限流配额、最小支持窗口。若是纯本地单机应用且无云依赖，本方案可整体暂缓，但要在立项包里写明理由与触发条件。

不预设：REST/gRPC/GraphQL、版本机制、鉴权方式、旧版本支持窗口。所有具体值由项目决定，未核实的标**待验证**。

## 开始写代码前，先让 AI 回答这些问题

1. 是否真的需要服务端？哪些功能依赖它，离线时各功能的预期是什么（→《网络与离线弹性技术方案》）？
2. 接口清单：每个接口的名称、用途、请求/响应结构、字段口径、安全要求、owner、版本（→《数据模型与数据契约方案》的字段字典）？
3. 契约由谁定义（OpenAPI/proto/Go struct 单源生成）？前端类型与后端模型是否同源、有 parity 门（→《绑定层契约与生成物方案》《配置文件方案》）？
4. 版本机制是什么（URI / header / media type / 字段共存 + 适配器）？**什么算 breaking change**，有无成文目录？
5. 旧客户端最小支持窗口多长？强制升级策略与用户提示是什么（→《应用内更新体验方案》）？
6. 新增字段、收紧枚举、改状态码、改分页语义分别怎么处理？废弃字段如何标注 sunset 并驱动兼容性工具？
7. 错误契约：结构化错误（码 + 字段 + 可重试 + 关联 ID）在各层如何映射？中间层只 wrap 不重新编码（→《状态码方案》《Go测试与文件系统模式方案》）？
8. 限流/配额：按用户、设备还是租户？超限返回什么、客户端如何退避与展示（→《防抖与节流方案》《网络与离线弹性技术方案》）？
9. 认证变化（新增 scope、改 token 格式）是否算 breaking change？如何协调灰度发布？
10. 幂等：重试、超时、重复提交、离线重放各自靠什么保证不产生重复实体（→《原子性提交方案》《网络与离线弹性技术方案》）？
11. 代理/自定义 CA/证书固定的策略是否与 Go 侧 HTTP 客户端一致（→《生产构建安全基线方案》《本地敏感数据与密钥管理方案》）？
12. 契约变更的评审人、门与追踪矩阵在哪（→《立项范围与决策记录方案》《CI矩阵与质量门禁方案》）？
13. 兼容性测试：旧客户端 × 新服务端、新客户端 × 旧服务端各跑哪些用例？

交付给 AI 的设计结果应包含：接口清单、契约单源与 parity、版本与 breaking-change 目录、错误契约、限流配额、幂等策略、支持窗口与兼容性矩阵。

## 核心纪律

### 一、契约优先，字段口径单源

| 项 | 要求 | 验收证据 |
|---|---|---|
| 定义 | 一份机器可读契约（OpenAPI/proto/生成用的 struct） | 契约文件 + 生成步骤 |
| 派生 | 前端类型、校验规则、文档、错误码从同一份派生或校验 | parity 测试；不一致 CI 失败（→《CI矩阵与质量门禁方案》） |
| 口径 | 时间 UTC、金额 minor unit、枚举未知值兜底、零值不兼职哨兵 | 字段字典（→《数据模型与数据契约方案》《格式化与货币本地化方案》） |
| 校验 | 边界层规范化与结构校验，领域层业务规则 | 四层校验位置（→《输入数据验证方案》） |
| 变更 | 先改契约与验收标准，再改实现 | 变更控制记录（→《立项范围与决策记录方案》） |

**「前后端联调靠猜」是契约缺失的典型症状**；接口清单里出现「以实际返回为准」就等于没有契约。

### 二、版本与 breaking-change 目录

| 变更 | 是否破坏 | 处理 |
|---|---|---|
| 新增可忽略响应字段 | 否（旧客户端需忽略未知字段） | 加字段 + 兼容测试 |
| 新增必填请求字段 | 是 | 新版本或双写过渡 |
| 删除/改义响应字段 | 是 | 废弃期 + sunset 标注 + 迁移窗口 |
| 收紧枚举/校验 | 是 | 显式目录 + 协调发布 |
| 改状态码/错误语义 | 是 | 错误契约版本化 |
| 新增认证 scope | 是 | 灰度与强制升级协调（→《登录与权限方案》） |

- 目录要**成文并进兼容性工具**，不是评审时口头判断；`experimental / stable / deprecated（带 sunset）/ removed` 状态随契约走。
- 版本机制选一种并写明为什么；适配器只做校验、字段映射、默认值与表示层转换，**不要长成第二套领域层**。
- 每个破坏性变更配：受影响旧客户端版本、迁移路径、强制升级提示、回滚方式。

### 三、错误、限流与幂等

- 结构化错误与错误码表同源；码决定事实，文案决定展示（→《状态码方案》《操作反馈方案》）。
- 区分「服务端故障」与「业务拒绝」，避免把 5xx 显示成「许可无效」或「参数错误」（→《授权与许可方案》同类纪律）。
- 限流配额写明维度与超限语义；客户端退避有上限、带抖动，超限提示可操作（→《网络与离线弹性技术方案》《防抖与节流方案》）。
- 幂等键由客户端生成并随重试/离线重放保持稳定；重试不改语义，重复提交不产生重复实体（→《原子性提交方案》《任务队列方案》）。
- 超时与重试矩阵按接口登记：哪些可重试、哪些必须询问用户（→《网络与离线弹性技术方案》）。

### 四、支持窗口与形态差异

- 旧客户端最小支持窗口是**产品承诺**：写明时长、强制升级策略、到期后行为与用户提示（→《应用内更新体验方案》）。
- 桌面客户端不像网页能瞬时全量更新：灰度期间必然多版本共存，服务端要按版本路由或兼容（→《签名打包与更新分发技术方案》《版本号方案》）。
- dev/server/打包安装三种形态的 base URL、代理、证书策略可能不同，差异成文并在安装态冒烟（→《生产构建安全基线方案》）。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 改字段名后旧版客户端崩溃 | 没有 breaking-change 目录与兼容测试 | 成文目录 + 双版本矩阵 |
| 前后端对「金额/时间」理解不一致 | 字段口径没单源 | 字段字典 + parity 门 |
| 新 scope 上线后老客户端全挂 | 把安全改进当「自动安全」 | 认证变更列入破坏性变更 + 灰度 |
| 重试产生重复记录 | 无幂等键、离线重放不稳定 | 客户端幂等键 + 服务端去重 |
| 限流被显示成「操作失败」 | 错误契约未分类 | 结构化错误 + 用户可操作提示 |
| 灰度期新服务端打断旧客户端 | 以为桌面能像网页瞬时更新 | 支持窗口 + 按版本路由 |
| 契约改了文档没改 | 文档手写、未从契约生成 | 单源生成 + CI diff 门 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 契约 | 生成物 diff、字段口径、未知字段忽略、未知枚举兜底 |
| 兼容 | 旧客户端 × 新服务端、新客户端 × 旧服务端；每个破坏性变更一条用例 |
| 边界 | 最小/最大长度、枚举边界、分页边界、空集合 |
| 错误 | 4xx/5xx/限流/超时/离线各自的用户提示与退避 |
| 幂等 | 重试、重复提交、离线重放、乱序到达 |
| 形态 | dev / server / 打包安装的 base URL、代理、证书差异 |
| 门禁 | 故意改一处契约不更新生成物，确认门真的红 |

## 给 AI 的实施约束模板

> 先给出接口清单与机器可读契约、单源派生与 parity 门、版本机制与 breaking-change 目录、结构化错误契约、限流配额与幂等策略、旧客户端支持窗口与兼容性矩阵，再写请求代码。**契约优先且字段口径单源；新增必填字段、删除/改义字段、收紧枚举、改状态码、新增认证 scope 都算破坏性变更；废弃项标 sunset 并驱动兼容性工具；适配器只做校验/映射/默认值，不长成第二套领域层；幂等键由客户端生成且重试/离线重放保持稳定；桌面多版本共存要按版本路由。** 变更先改契约与验收标准再改实现，任何「以实际返回为准」视为契约缺失。实现后生成旧×新、新×旧的兼容性测试与故意失败用例，并列出未覆盖形态。所有版本机制、窗口、配额由当前项目需求决定。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 是否依赖服务端的决策、契约单源原则 |
| 二档 | 接口清单、版本机制、错误契约、幂等与限流 |
| 三档 | 兼容性矩阵、灰度期多版本路由、支持窗口 |
| 四档 | parity 与 breaking-change 门进发布门禁、强制升级提示 |
| 五档 | 纯本地单机应用可整体暂缓，但须在立项包写理由与触发条件（出现第二台设备/云端副本/账号体系时重评，→《多端数据同步方案》《登录与权限方案》） |
