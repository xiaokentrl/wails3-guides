# 数据模型与数据契约方案：通用规划方案

## 这份方案是做什么的

来源：主大纲一档「事实源与权威状态归属」「领域切分」两项，以及行业数据建模/立项评审清单里反复出现的几类「改不动」的决策——主键策略、时间口径、软删除与历史、schema 演进、数据分类与保留。

母法方案：《应用状态与持久化技术方案》（落盘、迁移、备份与损坏降级）、《输入数据验证方案》（四层校验职责）、《统一同步层技术方案》与《UI数据一致性实现方案》（事实与镜像）、《多端数据同步方案》（oplog、tombstone、冲突裁决与 HLC）、《状态码方案》（枚举前向兼容）、《格式化与货币本地化方案》（时间/数字的区域格式与 DST）。

现有专题分别管「状态怎么存」「数据怎么校验」「界面怎么同步」「多端怎么合并」，但没有一篇管**数据本身长什么样**：有哪些实体、用什么 ID、时间以什么口径存、删除是物理还是标记、字段变了旧数据怎么办。这些决策一旦落地，事后改动要动的是每一份已发出去的用户数据，比换框架贵得多。

不预设：数据库产品、ORM、是否联网、是否有账号、ID 格式、保留期限。具体值由项目决定，未核实的标**待验证**。

## 开始写代码前，先让 AI 回答这些问题

1. 领域清单与每个领域的「写操作清单」是什么？唯一权威入口在哪（主大纲一档）？
2. 每个实体/值对象的字段、基数、必填性、唯一约束是什么？访问模式（怎么查）先于抽象关系？
3. 主键策略：自增整数、UUIDv4、UUIDv7/ULID、内容哈希，各自理由？是否可能把业务字段（邮箱、路径、名称）当主键？
4. 稳定 ID 与显示名是否分离？改名、合并、拆分实体时 ID 是否保持不变（→《托盘技术方案》身份映射纪律）？
5. 时间：存储用 UTC 还是带时区？时长用单调时钟还是墙钟？事件排序用本地序号、时间戳还是混合逻辑时钟（→《多端数据同步方案》）？
6. 是否持久化格式化后的字符串（日期、金额、带千分位的数字）？还是只存规范化值（→《格式化与货币本地化方案》）？
7. 删除语义：物理删除、软删除、归档？恢复窗口多久？删除后是否可能通过同步「复活」（→《多端数据同步方案》的 tombstone）？
8. 「未设置 / 未知 / 空」如何表达？**零值是否兼职哨兵**（→《窗口与多窗口技术方案》里 `0,0` 不能兼职未记录）？
9. schema 版本与迁移策略：加列优先？可空→回填→收紧？降级到旧版本时旧版能否识别并明确拒绝新 schema？
10. 审计字段：创建/更新时间、操作者、关联 ID、来源，哪些是必须的（→《日志与可诊断性技术方案》）？
11. 数据分类与留存：每类数据存哪、留多久、谁负责删、删除覆盖哪些副本（→《本地敏感数据与密钥管理方案》《磁盘资源缓存管理方案》）？
12. 数据可携带性：是否需要导出/导入回环？导出格式是否含 schema 版本？导入旧版本数据怎么处理？
13. 枚举与码值：新增值旧客户端怎么处理？改义是否禁止（→《状态码方案》）？
14. 需求↔设计↔实现↔测试的追踪矩阵在哪（→《立项范围与决策记录方案》）？

交付给 AI 的设计结果应包含：领域/实体清单、字段字典、ID 与时间策略、删除与历史策略、schema 演进规则、分类与留存表、审计字段、导出/导入契约、追踪矩阵。

## 核心纪律

### 一、领域边界：先定「谁写」，再定「长什么样」

| 项 | 要写清 | 验收证据 |
|---|---|---|
| 领域清单 | 每个领域的边界、拥有的实体、唯一的写入口 | 领域清单 + 写操作清单 |
| 权威 | 哪些数据是事实、哪些只是投影/镜像（→《统一同步层技术方案》） | 事实源标注；前端不得持有长期权威副本 |
| 聚合 | 一次命令的事务边界覆盖哪些实体（→《原子性提交方案》） | 命令三问登记表 |
| 投影标识 | 前端的投影 key 能否与领域/实体一一对应 | 投影标识映射表 |

**「先画 ER 再想查询」和「先想页面再倒推表」都容易翻车**：建模按实际访问模式定，同时用领域边界防止一张表被五个模块各写一半。

### 二、ID、时间与零值：三个不可事后改的口径

| 决策 | 判定表 |
|---|---|
| 主键 | 单机自增整数（简单、可排序，但合并/多端会撞）；UUIDv4（不可预测、索引局部性差）；UUIDv7/ULID（可排序、分布式安全）——**按是否存在多端/合并需求选，不按流行度选**；内容哈希适合内容寻址缓存（→《磁盘资源缓存管理方案》） |
| 稳定 ID | 与显示名、路径、资源名分开；显示名本地化/改名不得改变稳定 ID 与单实例锁、数据目录、升级识别 |
| 时间 | 存储 UTC + 明确精度；展示时才按 locale/timeZone 格式化；DST 与本地午夜解析交给《格式化与货币本地化方案》；时长/超时用单调时钟，不用墙钟差 |
| 排序 | 单机用单调序号；跨设备/离线写入用 HLC 或显式版本号并写明冲突裁决（→《多端数据同步方案》） |
| 零值 | `0`、`""`、`null` 各自含义固定；**禁止用零值同时表示「未记录」和「合法值」**，需要独立 `hasX` / 可选类型；时间零值不得表示「永不过期」 |
| 枚举 | 未知值必须有兜底分支；码值冻结不复用、不改义（→《状态码方案》） |

### 三、删除与历史：删除是最容易被低估的写操作

- 先回答「删了还能不能恢复、恢复窗口多久、谁有权限恢复」，再选物理删除/软删除/归档。
- 有同步或备份时，**软删除必须有 tombstone**，否则旧设备/旧备份的重放会把数据复活（→《多端数据同步方案》）。
- 保留期与删除触发要按存储位置登记：主库、缓存、日志、备份、导出、诊断包各有 owner（→《本地敏感数据与密钥管理方案》）。
- 受监管市场的「删除权/可携带权」要求导出与删除是**可重复执行的流程**，不是一次人工 SQL；删除要能覆盖副本并留下可审计记录。
- 历史/审计表与业务表分开，避免「为了留痕把业务表撑成日志表」；关联 ID 贯穿（→《日志与可诊断性技术方案》）。

### 四、schema 演进：只做可回滚的加法

| 变更 | 顺序 | 禁止 |
|---|---|---|
| 加字段 | 可空 → 双写/回填 → 收紧约束 | 一次性加非空且无默认值 |
| 改类型/改义 | 新字段 + 迁移 + 旧字段废弃期 | 原地改义、复用旧字段名 |
| 删字段 | 停写 → 观察期 → 停读 → 删除 | 直接删导致旧版读不了 |
| 版本守卫 | 每次迁移前预备份、记录 schema 版本 | 静默打开新 schema |

**降级保护是硬要求**：用户从新版本退回旧版本，旧版必须能识别并拒绝打开新 schema，而不是静默损坏（→《应用状态与持久化技术方案》）。迁移流程要有演练记录与失败回退路径，且不得把「读侧兜底」当成「写侧可以写坏值」的许可。

### 五、字段字典与契约表

每个持久化字段登记：名称、类型、口径（单位/时区/编码）、是否可空、默认、分类（公开/内部/敏感）、owner、引入版本、废弃计划。字段字典是**单源**：落盘 Schema、绑定模型（→《绑定层契约与生成物方案》）、配置 Schema（→《配置文件方案》）、导出格式、错误码枚举都从它派生或校验，不一致时 CI 明确失败。

导出/导入契约写明：格式版本、schema 版本、未知字段处理、校验和、幂等导入（重复导入不产生重复实体）、失败时保留原数据。导入是外部输入，走《输入数据验证方案》的规范化与消毒，不直接拼路径或反序列化任意类型。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 改名后单实例锁/数据目录/升级识别全乱 | 显示名当稳定 ID 用 | 身份映射表 + 稳定 ID 与显示名分离 |
| 多屏/多端下记录顺序错乱 | 用墙钟时间戳排序，时钟回拨或离线写入 | 单调序号或 HLC + 冲突裁决登记 |
| 用户把值设为 0 后「没保存」 | 零值兼职未记录哨兵 | 独立 `hasX` / 可选类型 |
| 删掉的数据又出现了 | 无 tombstone，旧设备重放 | 软删除 + tombstone + 重放幂等 |
| 降级后数据损坏 | 新 schema 无版本守卫 | 预迁移备份 + 版本守卫 + 明确拒绝 |
| 对账差一分 / 生日差一天 | 存了格式化字符串或本地时间 | 存规范化值 + UTC，展示层才格式化 |
| 新增枚举值旧客户端白屏 | 无未知值兜底分支 | 枚举前向兼容 + parity 门 |
| 导出导入后重复记录 | 导入不幂等、无格式版本 | 稳定 ID + 幂等重放 + schema 版本 |
| 删除请求只删主库 | 副本无留存策略 | 按存储位置登记删除 owner |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 约束 | 唯一约束、必填、边界值、空集合、超长字段（→《输入数据验证方案》） |
| 迁移 | 逐版本升级、跨版本跳升、降级被拒、迁移中断后重启、预迁移备份可用 |
| 删除 | 软删除恢复窗口、tombstone 防复活、删除覆盖副本、重复删除幂等 |
| 时间 | 时钟回拨、DST 切换、跨时区展示、本地午夜解析、时长用单调时钟 |
| 零值 | 合法 0/空字符串与「未记录」分别落盘并读回 |
| ID | 改名不改 ID、合并/拆分、导入重复 ID、内容寻址命中 |
| 导出 | 回环导入数据一致、未知字段、格式版本不匹配、失败保留原数据 |
| 一致性 | 非 UI 路径改事实后各表面收敛（→《UI数据一致性实现方案》）、绑定模型与字典 parity |

## 给 AI 的实施约束模板

> 先给出领域/实体清单与写操作清单、字段字典（含口径与分类）、ID/时间/零值策略、删除与历史策略、schema 演进与降级保护、留存与副本删除表、导出/导入契约，再开始建表。**稳定 ID 与显示名必须分离；时间统一 UTC 存储、展示层才格式化；零值不得兼职「未记录」哨兵；有同步或备份的软删除必须配 tombstone；迁移前预备份且旧版本必须能识别并拒绝新 schema；枚举新增值要有未知值兜底。** 字段字典作为单源，落盘 Schema、绑定模型、导出格式与它不一致时 CI 明确失败。不得凭「先这样以后再改」跳过 ID 与时间口径决策——这两类改动要动已发出去的用户数据。实现后给出迁移、降级、删除恢复、导出回环、时钟回拨的可观察测试，并列出未实测平台。所有数据库产品、ID 格式、保留期限由当前项目需求决定。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 领域清单与写操作清单、事实源归属、ID 与时间口径（不回答不写业务代码） |
| 二档 | 字段字典、零值语义、删除与历史、schema 演进与降级保护——第一个可分发里程碑前锁定 |
| 三档 | 审计字段、导出/导入回环、非 UI 一致性冒烟 |
| 四档 | 留存与删除自动化、字典单源 parity 门、受监管市场的删除请求响应路径 |
| 五档 | 复杂历史/版本回溯、多租户建模可按产品形态暂缓，每笔写理由 + 触发重新评估的条件 |
