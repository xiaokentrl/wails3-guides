# 可扩展插件支持：Wails3 + Go 专用方案

## 这份方案是做什么的

当应用需要「第三方或用户扩展能力」时，本方案回答：**扩展到什么程度、插件长什么样、怎么加载、怎么管住**。它把一个被严重低估的事实放在最前面：

> **插件系统一旦发布，插件 API 就是公共契约**——改一行签名都是破坏性变更，冻结成本随用户数增长。所以第一决策不是「怎么实现插件」，而是「需不需要动态插件」。

纪律母法的落点：第三方代码 = 不受信内容（→《安全边界与权限技术方案》）；插件产生的变更走统一落定层（→《统一同步层技术方案》）；插件耗时工作进任务队列（→《任务队列方案》）；插件贡献的命令进命令注册表（→《菜单方案》）。

## 第一步：分级决策（先选档，再设计）

| 档位 | 形态 | 覆盖的需求 | 代价 |
|---|---|---|---|
| **0 档：扩展点** | 接口 + 注册表，扩展**编译进应用**（内置的导出格式、导入器、面板） | 绝大多数「可扩展」诉求 | 几乎为零；API 可重构（编译期检查） |
| **1 档：内嵌脚本** | 内嵌解释器（yaegi / Lua），用户脚本进程内运行 | 用户自定义小逻辑 | 沙箱有限、性能受限、脚本 API 仍需冻结 |
| **2 档：子进程插件** | 独立进程 + stdin/stdout JSON-RPC，宿主仲裁能力 | 真第三方、闭源分发、崩溃隔离 | IPC 协议设计、生命周期管理、版本兼容——**真正的长期契约** |
| **不做的** | Go `plugin` 包（**不支持 Windows**，桌面三平台直接出局）；加载任意 .dll/.so；给前端插件完整绑定 | — | 安全灾难 |

**决策规则**：默认 0 档起步；出现「用户/第三方要在不改应用的情况下加东西」的真实需求才升档；升到 2 档前必须先回答分发与信任问题（谁签名、从哪装、用户如何确认）。**每升一档都要重新立项**，因为 API 冻结等级完全不同。

## 通用底座：扩展点注册表（0 档也是它）

无论哪档，扩展点先立为**接口 + 注册表**：

```go
// internal/extensions/ —— 扩展点契约
type ExtensionPoint[T any] interface {
    Register(id string, impl T) error   // 启动期注册，ID 稳定
    All() []T
}

// 扩展点示例（按项目需求定义，不预先造满）：
// Exporter  —— 导出格式（MIME、导出函数）
// Importer  —— 导入解析
// Panel     —— 侧栏面板（声明式贡献，见下）
// Command   —— 命令贡献（直接进菜单方案命令注册表，Surfaces 声明）
```

- 扩展点接口**只含数据容器与窄接口**（→ 绑定类型禁区同理）；接口一经第三方可见即冻结，内部重构用适配层隔离。
- 扩展点在立项时按需求清单定义，**不为想象中的插件预造扩展点**——空的扩展点是负资产。

## 2 档：子进程插件的设计要点

选了动态插件，以下每条都是必答题：

### 插件清单（manifest）
```toml
id = "com.example.csv-export"        # 反向域名，全局唯一（→ 主大纲身份单一源同理）
apiVersion = "1"                     # 宿主 API 大版本；不匹配 = 拒载并说明
version = "0.3.0"
permissions = ["tasks.submit", "facts.read:library", "menu.contribute"]
entry = "csv-export"                 # 可执行文件名（各平台打包 → 分发方案）
```

### 信任与加载
- **来源校验**：插件可执行文件验签（公钥内置 → 安全方案更新信任根）；来源分「应用市场签名 / 侧载」，侧载需用户显式确认并常驻提示。
- **权限模型**：manifest 声明权限，**宿主是唯一仲裁者（broker）**——插件拿不到数据库句柄、文件系统自由、网络自由；每项能力经宿主校验后代理。用户安装时看到权限清单并同意。
- **零直接共享**：插件与宿主零共享内存、零共享状态；一切经协议。

### IPC 协议
- stdin/stdout 行分隔 JSON-RPC（或本地 socket，二选一记录）；**协议自带 apiVersion 握手**，握手失败即拒载。
- 请求有超时、响应有上限（payload 尺寸）；插件无响应 = 视为挂起，可被宿主终止。
- 所有事件单向：插件 → 宿主「请求」；宿主 → 插件「通知」。插件不得监听端口、不得反向连接。

### 生命周期与隔离
```
发现 → 验签+清单校验 → 握手 → 注册贡献（命令/扩展点） → 激活
  → （运行：经宿主仲裁的能力调用）
  → 停用（撤销贡献，清理 UI 痕迹） → 卸载（数据目录询问后删除）
```
- **崩溃隔离是 2 档的存在理由**：插件进程死 → 宿主存活 → 任务中心/状态栏提示「插件 X 已停止」，可重启插件；宿主绝不因插件 panic。
- 启用/停用是用户设置（→ 状态方案），停用即撤销全部贡献（菜单项、面板消失）。
- 资源约束：CPU/内存/日志量的 per-plugin 配额进可诊断性设计（→ 可诊断性方案），防一个坏插件拖垮宿主。

### UI 贡献的克制
- **声明式优先**：插件贡献面板/菜单/设置页用**数据描述**（宿主组件渲染）——一致性、主题、无障碍全由宿主保证（→ 组件库方案）。
- **任意 HTML 插件 UI 只在确有需求时开**，且运行在隔离容器中（独立 WebView 环境 + 一次性销毁 → 窗口方案；零宿主绑定，仅经 IPC），这是最后的手段不是默认。

### 数据与状态
- 插件自身设置经宿主的设置机制存 `plugins/<id>/` 命名空间（→ 配置文件方案），插件不自带持久化路径。
- 插件产生业务事实 → 只能经宿主 API 写入事实层，变更走 sync 枢纽失效（→ 同步层唯一出口纪律对插件同样生效）；**插件不得直读/直写数据库**。
- 插件耗时操作 → 提交进任务队列（`tasks.submit` 权限），进任务中心可见（→ 任务队列方案）。

## 验收清单

- [ ] 档位决策记录在案（0/1/2 档 + 升档触发条件）
- [ ] apiVersion 不匹配的插件被拒载，用户看得到原因
- [ ] 无签名/验签失败的插件无法加载；侧载有显式确认
- [ ] 权限拒绝：声明外的能力调用被宿主拒绝并留痕
- [ ] 插件进程 kill -9：宿主存活、贡献撤销、可重启插件
- [ ] 停用插件：菜单/面板/命令全部消失，无残留监听
- [ ] 卸载：数据目录按用户意愿清理
- [ ] 插件任务出现在任务中心且可取消；插件产生的变更在兜底窗口内收敛到界面
- [ ] 坏插件日志风暴被配额限流（→ 可诊断性方案）

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 想改一个扩展点签名，十几个插件全崩 | API 过早公开、无冻结纪律 | 分档决策 + 0 档编译期保护 |
| 插件拖垮应用 | 进程内加载、无隔离 | 2 档子进程隔离 |
| 插件读到全部用户数据 | 给了宽泛权限 | broker 仲裁 + 最小权限清单 |
| 停用后菜单项还在 | 贡献未随生命周期撤销 | 贡献注册/撤销成对 |
| 插件把配置改坏 | 插件直写配置文件 | 插件经宿主命名空间存取 |
| 版本升级后插件集体失效 | apiVersion 无握手、破坏性变更无缓冲 | 握手 + 大版本迁移窗口 |
| 坏插件刷爆日志/事件 | 无配额 | per-plugin 限流 |
| 插件 UI 风格割裂、暗色漏网 | 插件自带 HTML/CSS | 声明式贡献优先 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先给出档位决策与扩展点清单（只定义有真实需求的扩展点）。扩展点接口只含数据容器与窄接口，贡献经注册表登记；若到 2 档：manifest 必含 id/apiVersion/version/permissions/entry，验签后加载，apiVersion 握手失败拒载；宿主是唯一能力仲裁者，插件零直接共享（无 DB、无文件自由、无网络自由、无端口监听）；生命周期「注册贡献 ↔ 撤销贡献」成对；崩溃隔离必须演练（插件被杀宿主存活）；UI 贡献声明式优先；插件设置走宿主命名空间、耗时操作进任务队列、业务变更走 sync 枢纽。per-plugin 日志与事件配额就位。实现后跑验收清单，并明确列出未覆盖的组合。

方案确认后再改代码；升档（0→1→2）是立项级变更，AI 不得自行引入动态加载。

## 五档定位（与主大纲的衔接）

- **一档**：档位决策（多数项目一档 = 0 档扩展点，记录升档触发条件）。
- **二档**：扩展点注册表、命令贡献接入菜单方案。
- **三 / 四档**：2 档时——信任链、权限 UI、配额、分发（→ 签名打包方案）全量。
