# 特性开关与远程配置方案：通用规划方案

## 这份方案是做什么的

来源：特性开关生产实践（注册表含 owner/用途/过期、kill switch、渐进放量、评估上下文契约与最小 PII、离线求值失败回退、清理纪律）、行业发布清单「feature-flagged dark launch + canary 5%/25%/50%/100%」，以及主大纲四档「灰度发布」。母法方案：《配置文件方案》（配置分家与逐键降级）、《版本号方案》（版本单源）、《签名打包与更新分发技术方案》（通道与回滚）、《网络与离线弹性技术方案》（离线与失败策略）、《缓存一致性方案》（缓存级别与失效）、《遥测与隐私合规方案》（评估上下文与标识符）、《CI矩阵与质量门禁方案》（门禁）。

它管**「不发新版也能改变行为」的能力与它的代价**：开关注册表、求值上下文、渐进放量、kill switch、离线回退、清理。不管业务配置怎么写（→《配置文件方案》）、不管更新包怎么分发（→《签名打包与更新分发技术方案》）。

不预设：是否使用第三方开关服务、开关数量、放量比例、上下文属性。所有具体值由项目决定。

## 开始写代码前，先让 AI 回答这些问题

1. 是否真的需要远程开关？哪些场景（灰度、热修、kill switch、A/B、运营配置）？纯本地开关够不够？
2. 注册表：每个开关记录什么（ID、owner、用途、引入版本、默认值、过期日、清理条件、关联 ADR）？谁负责清理？
3. 求值上下文允许哪些属性、类型、缺失时怎么处理？**能否用假名/粗粒度属性替代账号 ID、邮箱**？
4. 规则是否可解释：开发者能否复现「为什么这个用户拿到这个变体」？规则链是否需要文档？
5. 默认值与回退：网络不可达、服务 5xx、配置损坏、超时时应用行为是什么？**离线时是否保持上一次已知值，且坏值不覆盖好值**？
6. kill switch：哪些高危能力必须有独立开关？谁有权触发、多久生效、如何验证真的停了？
7. 渐进放量：分组依据、每阶段的观察指标与检查点、回滚条件与操作（→《性能与资源基线技术方案》《崩溃上报与符号还原方案》）？
8. 开关与版本/通道的关系：旧客户端不认识新开关时怎么办？灰度期间多版本共存（→《客户端与服务端API契约方案》）？
9. 求值是否缓存？缓存级别、key 全输入、失效触发、单飞（→《缓存一致性方案》）？
10. 生产构建是否可能残留开发用开关或强制值（→《生产构建安全基线方案》）？
11. 开关变更是否需要审计留痕（谁、何时、改了什么、为什么）（→《日志与可诊断性技术方案》）？
12. 开关引入的债：临时开关到期未清理，如何被自动发现并进版本评审（→《测试策略与验收总纲》）？

交付给 AI 的设计结果应包含：开关注册表、求值上下文契约、默认值与失败回退矩阵、kill switch 清单、放量检查点、缓存与一致性策略、清理与审计流程。

## 核心纪律

### 一、注册表：每个开关有 owner 与过期日

| 字段 | 要求 |
|---|---|
| ID | 稳定标识，不用邮箱/账号等个人信息充当 |
| owner | 明确到人/团队，**没有 owner 的开关不许上线** |
| 用途与类型 | 灰度 / kill switch / 运营配置 / 实验，各自生命周期不同 |
| 默认值 | 本地内置的安全默认（通常关闭新能力） |
| 过期日与清理条件 | 到期自动报警并进版本评审；临时开关必须可删除 |
| 关联 | 关联 ADR、需求 ID、回滚 runbook（→《立项范围与决策记录方案》） |

**「先加个开关以后再删」是最常见的债**：没有过期日的开关会永久留在代码里，两年后没人敢动。

### 二、求值上下文与最小 PII

- 上下文契约列出允许的属性、类型、缺失处理；优先稳定标识与粗粒度属性（版本、渠道、平台、区域），不用账号 ID、邮箱、自由文本。
- 规则要可解释：给定上下文能复现变体；难以复现的长规则链是故障排查的噩梦。
- 远程配置里**不放密钥**：开关控制行为，密钥授予访问权限，两者不混（→《本地敏感数据与密钥管理方案》）。
- 评估上下文属于数据流，新增属性触发隐私复审（→《遥测与隐私合规方案》）。

### 三、失败回退：离线不能变成「行为随机」

| 场景 | 期望 | 禁止 |
|---|---|---|
| 网络不可达 | 用本地默认或上一次已知好值 | 每次启动行为不同 |
| 服务 5xx / 超时 | 保持上次值 + 可诊断记录 | 静默切到未知默认 |
| 配置损坏 | 逐键降级、坏值不覆盖好值（→《配置文件方案》《应用状态与持久化技术方案》） | 整体白屏 |
| 未知开关 ID | 忽略并按本地默认 | 抛异常终止启动 |
| 求值依赖未就绪 | 排队到依赖就绪（→《依赖顺序方案》） | 半初始化状态读配置 |

**回退行为要可测**：断网、5xx、损坏文件、超时四种场景各有用例，且断言「行为与上次一致」。

### 四、kill switch、放量与清理

- 高危能力（外部写入、同步、付费、自动更新、诊断上报）各有一个独立 kill switch；触发人、生效时限、验证方式写进 runbook（→《威胁建模与安全响应方案》的事件遏制）。
- 放量按阶段设检查点：单元/集成通过 → 灰度环境验证 → 小比例观察（崩溃率、错误率、性能指标）→ 逐级扩大 → 全量；**每阶段通过条件事先定义，不是看到数据再定**（→《崩溃上报与符号还原方案》《性能与资源基线技术方案》）。
- 回滚是操作，不是「把开关关掉」一句话：写明谁执行、多久生效、旧版本是否保留（→《签名打包与更新分发技术方案》）。
- 缓存求值结果按《缓存一致性方案》登记级别、key 全输入、失效触发与单飞；避免「同一用户两次求值不同」。
- 清理：过期开关自动进版本评审；清理时同时删代码分支、注册表、文档与测试，不留半截（→《公共函数与Helper方案》的三次规则同理）。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 断网后功能时有时无 | 无本地默认/上次好值，每次重新求值 | 失败回退矩阵 + 坏值不覆盖好值 |
| 没人敢删旧开关 | 无 owner、无过期日 | 注册表 + 到期报警 + 版本评审 |
| 用户拿到哪个变体说不清 | 上下文属性过多、规则链无文档 | 上下文契约 + 可复现规则 |
| 远程配置泄露凭据 | 把密钥当配置下发 | 开关/密钥分离（→《本地敏感数据与密钥管理方案》） |
| 灰度事故关不掉 | 无独立 kill switch 或无触发权限 | 高危能力逐项开关 + 遏制 runbook |
| 放量后问题扩大才发现 | 检查点与回滚条件事后定 | 阶段检查点事先定义 |
| 同一用户两次行为不同 | 求值缓存无一致性级别 | 缓存登记 + key 全输入 + 单飞 |
| 隐私评审漏了新属性 | 上下文变更未触发复审 | 数据流变更触发条件 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 求值 | on/off/未知 ID/上下文缺失/边界属性，断言可复现 |
| 失败 | 断网、5xx、超时、损坏文件、求值依赖未就绪 |
| kill switch | 每项高危能力触发→生效→验证→恢复 |
| 放量 | 每阶段检查点、回滚演练、指标观测 |
| 一致性 | 缓存级别、失效、单飞、同用户多次求值一致 |
| 形态 | dev / 打包安装；生产构建无开发用强制值 |
| 清理 | 故意留一个过期开关，确认报警与评审条目生成 |

## 给 AI 的实施约束模板

> 先给出开关注册表（ID/owner/用途/默认值/过期日/清理条件）、求值上下文契约、失败回退矩阵、kill switch 清单、放量检查点与回滚流程、缓存与一致性策略、清理与审计机制，再写求值代码。**没有 owner 与过期日的开关不许上线；上下文用稳定粗粒度标识、不用个人信息；开关控制行为、密钥授予访问，两者分离；断网/服务故障/配置损坏时用本地默认或上次已知好值且坏值不覆盖好值；高危能力各有独立 kill switch 并写清触发人与验证方式；放量检查点事先定义；过期开关自动进版本评审并连带清理代码、文档与测试。** 任何「先加个开关以后再删」视为登记债。实现后给出求值、失败、kill switch、放量的可观察测试，并列出未覆盖形态。所有开关类型、上下文属性、放量比例由当前项目需求决定。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 是否需要远程开关的决策、本地安全默认原则 |
| 二档 | 注册表、上下文契约、失败回退矩阵 |
| 三档 | kill switch、缓存一致性、审计留痕 |
| 四档 | 放量检查点、回滚演练、生产构建无开发强制值 |
| 五档 | 第三方开关服务与 A/B 实验平台可按产品阶段暂缓（写理由 + 触发条件）；本地 kill switch 不暂缓 |
