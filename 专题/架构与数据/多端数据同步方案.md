# 多端数据同步：通用规划方案

## 这份方案是做什么的

单机应用长出第二台设备（或云端副本）的那一刻，「谁是事实」就裂开了。本方案规划**本地优先应用的多端/云数据同步**：同步模型怎么选、冲突怎么裁决、删除怎么防止复活、离线队列怎么重放、UI 怎么呈现同步状态。

**与相邻方案的分工**：
- UI 与本机事实源的一致性 →《统一同步层技术方案》《UI数据一致性实现方案》——本方案不碰这条链。**云/其他设备的下行变更只是事实源的又一个修改入口**：落定后同样走 hub.Settle，前端照常收敛，不多写一行同步代码。这是本方案最重要的结构衔接。
- 离线行为与排队 →《网络与离线弹性技术方案》；任务化上传/下载 →《任务队列方案》；时钟不可信 → 同；凭据与账号安全 →《安全边界与权限技术方案》。

**硬性目标**：任何冲突都有**预先登记的裁决规则**，任何删除都有 tombstone，任何同步操作幂等可重放——「静默丢用户数据」「数据复活」「换号串数据」三类事故在结构上不可能发生。

## 第一步：同步模型分档（决定一切复杂度）

| 档 | 模型 | 覆盖 | 代价 |
|---|---|---|---|
| **1 档：单向** | 仅备份/导出到云，无下行 | 数据保险 | 极低，几乎只是存储 |
| **2 档：单写多读** | 一台主设备写，其他设备只读 | 个人主键 + 移动查看 | 低；无冲突 |
| **3 档：多写 LWW** | 多设备写，**按实体/字段**最后写入胜 | 协作弱、实体独立的场景 | 中；需要混合逻辑时钟 + 冲突可见性 |
| **4 档：多写合并** | 字段合并 / CRDT / 手动解决 | 强协作、并发编辑 | 高；算法与测试成本数量级上升 |

**决策规则**：逐**实体**选档（同一应用可以混合：设置用 3 档 LWW，文档正文用 4 档，日志用 1 档）。**默认从低档开始**——升档随时可以，降档要迁移用户数据。禁止「全应用统一一个模型」的偷懒：冲突域的定义比同步算法更重要。

## 核心机制

### 变更日志（oplog）——同步的地基
- 每个本地写操作记录一条日志：`(实体, 操作, 字段/载荷, 逻辑时钟, 设备ID, 同步状态)`；**写路径顺带落日志**（与业务写同事务或紧随其后），不做事后补账。
- 上行：按逻辑时钟序推送，**at-least-once + 服务端去重键**（设备ID + 序号）——可安全重放（与任务队列幂等纪律同形状）。
- 下行：服务端返回他端变更 → 按裁决规则合并 → **过领域层校验（他端设备同样不可信，不变式与任何入口一视同仁，→《输入数据验证方案》）** → 写入本地事实层 → `hub.Settle` → 界面收敛（同一落定链）。

### 冲突裁决（3/4 档）
- **逐实体登记策略**，写进数据字典：LWW 字段集、需合并字段集、需手动解决的类型。
- LWW 的时钟必须可信：**混合逻辑时钟（HLC）或服务器时钟**，本地墙钟只做展示（→ 网络方案时钟纪律——本地时钟偏差会静默吞掉一端写入）。
- **手动解决是兜底而非默认**：需要用户裁决的冲突要有专门的解决 UI（两版并排、选择或编辑），且**禁止静默丢弃任何一端**——拿不准时保留双份让用户选。
- 冲突解决本身也是一次本地写，走同一 oplog，不再产生新冲突。

### 删除：tombstone 或没有删除
- 删除 = 写入墓碑记录（ID + 删除时钟），**永不物理删除已同步实体**；墓碑保留期与全量对账周期配套（→ 状态方案）。
- 「删除 vs 他端修改」冲突：按登记策略裁决（通常删除胜或标记冲突），**杜绝复活**——「删掉的东西在另一台设备上回来」是同步应用最遭恨的事故。
- 墓碑清理必须有全量对账兜底（定期比对两端全量 ID 集），防墓碑丢失后的静默分叉。

### 首次同步与全量对账
- 新设备 bootstrap：全量拉取（分页/分块，大 payload 策略 → 主大纲绑定表）、进度可看（→ 任务队列）、可取消、中断可续。
- 定期全量对账（ID 集比对）作为增量同步的安全网——增量必有漏，对账是兜底。

### 账号与设备
- 设备注册/注销：注销设备的数据处理（拉黑 tombstone、撤销令牌）立项明确。
- **换号/登出**：本地数据与新账号的边界（清空 / 保留 / 提示合并）必须显式设计——「登出后新账号看到旧账号数据」是安全级事故（→ 安全方案敏感数据；登出生命周期 →《登录与权限方案》）。
- 同步令牌按设备隔离，单设备吊销不影响其他设备。

## UI 呈现（复用既有反馈体系）

- 同步状态是一份**事实**（synced / syncing / offline / conflict），住后端，经统一落定层到界面（→ 操作反馈方案矩阵登记）。
- 冲突待解决 = 需要行动的失败态：入口显眼、数量可见，**不弹窗打断**。
- 上传/下载长任务进任务中心，可取消可续（→ 任务队列）。

## 测试矩阵

| 维度 | 要覆盖的情况 |
|---|---|
| 并发 | 双设备并发写同实体（各字段 / 同字段）；三设备环形传播 |
| 冲突 | 修改 vs 删除；双方修改同字段；冲突解决后再冲突 |
| 离线 | 双端各自离线操作 N 条 → 恢复后按序重放 → 结果与预期裁决一致 |
| 删除 | 删除后他端修改；墓碑对账；删后再建同 ID 实体 |
| 时钟 | 本地时钟快/慢/回拨下的 LWW 裁决 |
| 中断 | 上行/下行中途断网 → 续传不重不漏 |
| 账号 | 登出→换号；设备注销后该设备变更被拒 |
| 规模 | 首次同步 10k+ 实体的时长与内存（→ 性能方案） |

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 删掉的数据在另一端复活 | 无 tombstone、物理删除同步 | 墓碑机制 + 对账 |
| 双端都改丢了一端 | 无逐实体裁决策略、本地墙钟做 LWW | 策略登记表 + HLC |
| 同步把数据写坏后无法回退 | 无变更日志、不可重放 | oplog 是地基 |
| 已同步内容反复重传 | 无去重键 | 设备ID+序号去重 |
| 同步风暴打爆服务端 | 无退避、无节流 | 指数退避 + 上行批量 |
| 换号看到旧账号数据 | 账号边界未设计 | 显式登出策略 |
| 首次同步卡死 | 全量无分页无任务化 | 分块 + 任务中心 |
| 两台设备永远各改各的 | 对账缺失、增量漏单 | 定期全量对账 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先给出同步模型分档决策（逐实体）与冲突裁决登记表。所有本地写经 oplog 记录（与业务写同事务），上行幂等可重放（设备ID+序号去重）；下行合并按登记策略，冲突禁静默丢弃，手动解决有专门 UI；删除一律 tombstone + 定期全量对账；LWW 用混合逻辑时钟，不信本地墙钟；下行变更落定走 hub.Settle，不另开界面刷新路径；首次同步分块任务化、可续传；登出/换号数据边界显式设计；同步令牌按设备隔离。同步状态作为事实进任务中心与状态表面。实现后跑测试矩阵（并发/冲突/离线/删除/时钟/中断/账号），并明确列出未覆盖的组合。

方案确认后再改代码；同步模型选型与裁决策略属产品决策，AI 给方案与推演，最终由用户裁决。

## 五档定位

- **一档**：是否需要多端同步 + 分档初判（多数单机应用在此记入暂缓）。
- **二档**：oplog 与上行通道、同步状态事实化。
- **三 / 四档**：冲突裁决全量、首次同步、全量对账、账号边界（→ 主大纲五档暂缓清单「多端 / 云数据同步」触发条件）。
