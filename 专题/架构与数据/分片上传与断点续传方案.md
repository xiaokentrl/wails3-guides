# 分片上传与断点续传：通用规划方案

## 这份方案是做什么的

大文件传输（上传/下载）超过单请求的可靠范围后，需要分片、断点续传、秒传与合并校验。本方案定**传输协议与工程纪律**：分片策略、七环协议、断点记账、失败恢复——组件侧只收集文件（`Upload` 的 `upload(file)` 契约不变），协议由调用方按本方案实现。

**与相邻方案的分工**：传输即长任务——取消/进度/暂停/任务中心 →《长任务与后台工作技术方案》；重试/超时/离线 →《网络与离线弹性技术方案》；断点记录持久化 →《应用状态与持久化技术方案》；进度呈现 →《操作反馈方案》与 GlobalProgressBar；分片原语（splitFile/chunkProgress）→ `ui/lib/upload.ts`；并发片数预算 →《性能与资源基线技术方案》。

**硬性目标**：
1. 断点续传**以服务端记账为准**（本地记录只做展示）——重启/换设备后从服务端已收片恢复；
2. 每片**幂等可重试**（uploadId + index 幂等键）、每片**有校验**、合并前**有终检**；
3. 源文件变更后旧断点**自动作废**——续传绝不传错文件。

## 第一步：分档决策（逐文件）

| 档 | 模型 | 适用 |
|---|---|---|
| 1 档 | 小文件直传（≤ 5 MB 单请求） | 头像、小附件——分片是过度设计 |
| 2 档 | 分片上传 | 大文件，网络可靠 |
| 3 档 | 分片 + 断点续传 | 大文件 + 不稳定网络 / 大到必须跨会话 |
| 4 档 | 秒传（按 hash 命中跳过传输） | 大量重复文件、服务端有存量 |

**判定规则**：默认 1 档；超阈值（建议 5–10 MB，按目标网络调整）升 2 档；断续网络或超大文件（100 MB+）升 3 档；秒传需要全量 hash 的成本评估（大文件全量 hash 读盘耗时——采样 hash 有碰撞风险，见下）。

## 上传协议七环

| 环 | 动作 | 关键纪律 |
|---|---|---|
| 1 **预检 init** | 文件指纹（hash + size + 名称）→ 服务端返回 `uploadId`、**已收片清单**（断点起点）、秒传命中则直接完成 | 指纹变化 → 旧断点作废、重新预检（源文件变更检测） |
| 2 **分片** | `splitFile(file, chunkSize)` 固定片大小（建议 4–8 MB；移动网络可调小） | 流式切片不整读文件进内存（→ 性能方案） |
| 3 **并发上传** | 片并发上限 2–4；失败片独立重试（幂等键 = `uploadId + index`，退避 + 上限） | 并发打爆带宽 → 队列上限（→ 任务队列并发纪律） |
| 4 **进度** | 已完成片字节 / 总字节 → 任务中心；节流合并（→ 防抖与节流方案） | 进度以**服务端确认**为准，本地发送 ≠ 完成 |
| 5 **片校验** | 服务端回传每片 hash（或 ETag），与本地比对 | 不匹配 → 单片重传，不拖全文件 |
| 6 **合并 complete** | 全片到位 → 合并请求 → 服务端校验片数与顺序 → **最终文件 hash 终检** → 文件可用 | 终检失败 → 报告并清理分片，不留损坏文件冒充成品 |
| 7 **清理** | 超时未完成的分片服务端回收（TTL） | 分片垃圾 = 磁盘缓存清理的同类问题（→ 磁盘资源缓存管理方案） |

## 断点续传纪律

- **双侧记账，服务端为准**：本地断点记录（已传片索引）只用于进度展示与发起优化；恢复时**必须重新预检**拿服务端已收片清单——本地记录与服务器不同步时，以服务器为准，多传一片的代价远小于丢一片；
- **下载对称**：下载断点续传 = `Range: bytes=N-` 请求 + 本地半成品文件追加；半成品用固定扩展名（`.part`），完成时**原子改名**（→ 状态方案原子写）；半成品残留由启动清扫兜底（→ 长任务方案）；
- **暂停 ≠ 取消**：暂停保留 `uploadId` 与断点；取消 = 通知服务端清理分片 + 清本地记录——两种语义在任务中心呈现不同按钮；
- **上传中源文件变更**：预检指纹在每片上传时抽查（或监听文件变更事件）——变更即作废当前任务并告知用户。

## 安全纪律

- `uploadId` 与账号绑定：越权续传他人上传被服务端拒绝；
- 每片请求鉴权（令牌）或使用**过期签名 URL**（URL 泄漏窗口有限，→ 安全方案）；
- 合并前服务端校验类型与大小上限（扩展名/魔数，→ 输入验证方案文件导入行）。

## 与任务队列的集成

- 每个传输 = 一个**任务**（kind 注册：`upload.file` / `download.file`，`Durable: true`——重启续跑）；
- 进度经节流上报进任务中心；取消走统一取消链（→ 任务队列）；
- 多文件并发 = 多任务 + 队列并发上限自然约束。

## 测试矩阵

| 维度 | 要覆盖的情况 |
|---|---|
| 断点 | 上传 30% 断网 → 重试只传剩余片；kill -9 重启 → 预检恢复 |
| 幂等 | 同片重复上传不产生副作用 |
| 校验 | 单片损坏 → 单片重传；合并终检失败 → 清理并报告 |
| 秒传 | 命中/未命中；采样误判（若启用采样） |
| 变更 | 传输中源文件修改 → 任务作废告知 |
| 并发 | 多文件并发上限；单片失败重试不影响其他片 |
| 下载 | Range 续传、半成品残留清扫、完成原子改名 |
| 内存 | 大文件切片/哈希全程流式，内存无台阶（→ 性能方案） |

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 上传到 99% 永远完不成 | 合并无终检 / 分片丢失无记账 | 七环第 5、6 环 |
| 断点续传传错文件 | 源文件变更未检测、本地断点当真 | 指纹作废 + 服务端为准 |
| 重启后从头再传 | 断点未持久化、预检缺失 | Durable 任务 + init 已收片 |
| 服务端堆满半成品分片 | 无 TTL 清理 | 第 7 环回收 |
| 秒传误判同文件 | 采样 hash 碰撞 | 全量 hash 或强采样 + 服务端复核 |
| 带宽被传输吃满 | 无并发上限 | 片并发 2–4 |
| 合并后文件损坏 | 无片校验无终检 | 第 5 环 |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先给出分档决策与协议七环设计（init/分片/并发/进度/片校验/合并/清理），分片参数与并发上限数值化。断点续传以服务端记账为准：恢复必须重新预检，本地记录仅展示；每片幂等（uploadId+index）+ 独立重试（退避+上限）+ 片校验；合并带终检，失败清理不留损坏文件；源文件指纹变更即作废任务；传输任务化（Durable + 任务中心 + 取消/暂停双语义）；上传中指纹抽查；服务端分片 TTL 清理。全程流式（切片/hash/上传不整读内存）。实现后补断点、幂等、校验、并发与 kill -9 恢复的测试（可用内存 Mock 协议），并明确列出未覆盖的协议变体。

方案确认后再改代码；协议字段与服务端能力属接口决策，AI 给设计与推演，最终由用户与服务端共同裁决。

## 五档定位

- **一档**：分档决策 + 协议七环设计 + 分片参数。
- **二档**：七环落地 + 任务化（Durable）+ 进度接线。
- **三 / 四档**：秒传、多端同步衔接（→ 多端数据同步方案）、服务端 TTL 治理全量。
