# 多平台一致组件库：公共组件方案

## 这份方案是做什么的

Wails3 应用的界面跑在**三个渲染引擎**上（Windows WebView2/Blink、macOS WKWebView、Linux WebKitGTK，后者行为接近 Safari），原生面（菜单、对话框、通知、托盘、文件选择）又各不相同。本方案规划一套**公共组件库**：三平台行为一致、视觉由令牌控制、跨项目积累复用。

**一致性的定义要先立正**：不是三平台像素相同——那既做不到也不该做（macOS 用户期待 Cmd 而非 Ctrl）。一致性指：

1. **语义与行为一致**：同一组件在三个平台有相同的角色、状态、键盘交互、错误行为；
2. **视觉由令牌控制**：外观差异只来自设计令牌与已声明的平台尊重点，不来自引擎默认样式或各写各的 CSS；
3. **平台差异显式声明**：每一处「有意跟随平台」的差异登记在案，无「无意中不一致」。

两个定位先说清：

- 组件库是**跨项目资产**，与 `guides/` 同哲学——积累、查重、整体迁移；不是单项目的一次性 UI 代码。
- 通用纪律的落点：IME 与文案 →《国际化与输入技术方案》《多语言实现方案》；键盘与读屏 →《无障碍与辅助技术方案》；系统能力前置 →《系统能力与平台集成技术方案》；窗口与几何 →《窗口与多窗口技术方案》。本方案管「组件怎么建、怎么保一致、怎么积累」。色彩的**内容规则**（调色板、明暗派生、对比度）见《主题与色彩方案》；交互反馈契约见《操作反馈方案》；前端落位见《前端目录结构方案》。

## 核心判定规则（先立规则，再列组件）

**一个交互走 Web 自绘还是走原生？** 一句话规则：

> **面向内容与工作流的交互一律 Web 自绘**（一致性、可测、可主题化）；**涉及系统资源与系统身份的入口走原生 + 统一 API 封装**（文件选择、系统通知、macOS 菜单栏、托盘）。

**平台尊重清单**（有意差异，登记在案，不算不一致）：

| 尊重点 | 行为 |
|---|---|
| 修饰键 | macOS 用 Cmd、其余用 Ctrl——组件只能引用修饰键令牌，不得硬编码 |
| 菜单栏归属 | macOS 原生菜单栏；Windows/Linux 应用内自绘菜单栏（或顶部窗口菜单，随项目定并声明） |
| 滚动条 | 跟随平台习惯（overlay 与占位差异），但用统一 ScrollArea 封装 |
| 文件/目录/保存对话框 | 永远原生（→ 系统能力方案），不做 Web 模拟 |
| 系统通知 | 原生优先，Web toast 作降级 |
| 系统 accent 色 / 深色模式 | 有令牌位承接，跟随系统 |
| IME 组合态 | 所有输入类组件遵守组合态纪律（→ 国际化方案），这是行为一致的一部分 |

**引擎兼容基线**（三引擎：Blink / WKWebView / WebKitGTK）：

- 引擎格局：WKWebView 与 WebKitGTK 同属 WebKit、彼此接近；与 Blink 的差异主要是 CSS 特性上线时序（Blink 常先发）与渲染细节。
- **已知坑**（立项时在锁定版本上核实并记录）：WebKitGTK 字体渲染偏粗（有公开 bug，Tauri/Wails 均受影响）；Linux 图形栈问题可能白屏或渲染毛刺；macOS 的 WKWebView 版本被系统锁死，旧系统 = 旧引擎；WebKitGTK 现代化 API 曾滞后于 Blink。以上行为随项目锁定版本**待验证**，核实结果写进基线文档。
- **基线纪律**：新 CSS/JS 特性三引擎核查（caniuse + 目标环境实测）后才可入库；不支持的必须带功能检测 + 降级；基线随 Linux 基线（WebKitGTK 6.0，随 Ubuntu 26.04）更新并记录版本号。稳妥策略：新特性先按 Safari 兼容性评估（WebKitGTK 与 WKWebView 同源）。
- **与 CSP 的衔接**（→ 安全方案）：组件库不得依赖内联事件处理器；CSS-in-JS 方案与 `style-src` 的兼容性在选型时验证，冲突则选零运行时样式方案（CSS Modules / 编译期方案）。

## 设计令牌：一致性的地基

- **令牌单源**：语义化令牌（`bg / surface / border / text / text-muted / primary / danger / warning / success / focus`；间距、圆角、阴影、动效时长、字阶、行高），单一来源生成 CSS variables + TS 常量。
- **禁止裸值**：组件样式只允许引用令牌；lint 或审查脚本扫描裸色值 / 裸尺寸 / 裸 z-index。暗色模式「漏网组件」的根因几乎都是裸色值。
- **主题 = 换令牌集**：明暗两套令牌集，组件零条件样式分支；平台 accent、高对比模式各是一个令牌集变体。
- **字体决策**（立项时二选一并记录）：内嵌字体（视觉完全一致，付体积与授权代价）或系统字体栈（零成本，接受平台渲染差异并声明）。**CJK 回退链必须显式声明**——中文回退到宋体还是黑体，直接决定三平台观感。WebKitGTK 偏粗问题若有，在此层统一校正（font-weight 令牌映射），不散落在组件里。
- **密度与缩放**：尺寸用相对单位；缩放档位进测试矩阵（→ 无障碍方案）；DIP 策略由窗口方案管，组件不自行换算像素。

## 组件清单（全面盘点）

每行标注实现方式：**自绘**（Web 渲染保一致）/ **桥接**（原生 + 统一 API）/ **混合**。

### 1. 输入与选择
Button / IconButton（自绘）· Link（自绘，外链走桥接 scheme 白名单）· TextInput / Textarea / Search（自绘，IME 组合态纪律 + 字数、校验呈现）· Select / Combobox（自绘 listbox，虚拟化长列表）· Checkbox / Radio / Switch（自绘——原生表单控件三平台观感各异，必须自绘）· Slider · NumberInput（步进、格式化走展示层）· DatePicker / TimePicker（自绘，区域格式 → 多语言方案）· ColorPicker（自绘，可复用系统取色器为平台尊重点）· FileInput（桥接原生文件对话框）· Tag / Chip · Badge · Avatar · Kbd。

### 2. 展示与布局
Typography 阶梯（字阶令牌驱动）· Stack / Grid / Container · Card · Divider · ScrollArea（统一滚动条与 overlay 行为）· SplitPane / Resizable · Tabs · Accordion · Breadcrumbs · Pagination · Table（排序 / 筛选 / 选择 / 虚拟化，大数据量 → 性能方案）· Tree · List + VirtualList · Timeline · DescriptionList · StatCard · Image（占位 / 加载失败态统一）。

### 3. 反馈与浮层
Modal / Dialog（焦点陷阱与归还 → 窗口方案模态规则）· Drawer / Sheet · Popover（定位三引擎一致，翻转逻辑统一实现）· Tooltip（延迟、触摸行为统一）· Toast（应用内反馈）· Alert / Banner · Confirm 系列（危险操作二次确认的统一形态）· ContextMenu（**自绘**——右键菜单是工作流交互，走 Web 保一致；仅托盘菜单走原生）· EmptyState / ErrorState · 全局 Loading 遮罩。

### 4. 导航与壳
AppShell（侧栏 + 顶栏布局骨架）· MenuBar（混合：macOS 原生菜单栏 + 其余自绘，同一份菜单定义双端渲染）· CommandPalette（Cmd/Cmd+K 统一入口，修饰键令牌）· SideNav / TreeNav · 快捷键总表（应用级注册中心，见横切体系）。

### 5. 表单体系
Form 容器（校验时机统一：组合态不校验、blur / 提交校验）· FieldLabel / 帮助文本 / 错误呈现（错误文案走语言包 → 多语言方案）· 必填与禁用语义统一。校验架构（分层职责、规则单源、错误协议）→《输入数据验证方案》。

### 6. 原生桥接层（统一 API 封装，Go 绑定之上再包一层）
FilePicker / FolderPicker / SaveDialog · MessageBox（原生消息框）· SystemNotification（原生 + Web toast 降级，前置条件 → 系统能力方案）· Clipboard（文本 / 富文本 / 图片的三引擎差异封装）· OpenURL / OpenFile（scheme 白名单 → 安全方案）· DragDrop zone（`EnableFileDrop` → 系统能力方案）· Print · TrayMenu 封装（→ 托盘方案）· GlobalShortcut（→ 系统能力方案）。桥接层是**平台分支唯一允许集中存在的地方**。

### 7. 图标体系
单一来源的一套单色线性图标，tint 走令牌；**一套中性图标走三平台，不逐平台换皮**（决策可反，但必须二选一并声明，不许半套一套）。模板图标需求（macOS 托盘）→ 托盘方案。

## 组件卡：库的积累单元

每个组件随源码交付一张**组件卡**（Markdown，与组件同目录），包含：

1. API 与用法示例（可运行）；
2. **状态矩阵**：default / hover / active / focus-visible / disabled / readonly / loading / error / empty / 暗色 / RTL / 缩放档位；
3. **键盘交互表**（Tab / 方向键 / Escape / Enter 各做什么）；
4. **平台尊重点**（引用尊重清单条目，无则写「无」）；
5. **引擎差异备注**（已知渲染差异与 fallback）；
6. a11y 语义（角色 / 名称 / 状态，→ 无障碍方案）；
7. 三平台截图。

没有组件卡的组件不算入库——这是「积累成库」和「攒了一堆代码」的分界线。

## 横切体系（先于组件建设）

- **焦点体系**：统一的焦点可见令牌、焦点顺序规则、模态陷阱实现、列表 / 菜单 / Tabs 的 roving tabindex 统一实现——所有组件复用，不各写各的。
- **快捷键注册中心**：应用级单一注册点，组件声明所需快捷键而非自行 `addEventListener`；修辭键走令牌；与 IME 组合态、全局快捷键的规则衔接（→ 国际化方案、系统能力方案）。
- **文本与国际化**：组件文案一律走语言包（→ 多语言实现方案）；布局用 CSS 逻辑属性（`margin-inline` 等），RTL 是令牌级翻转而非组件分支。
- **z-index 与浮层管理**：统一层级令牌，防止 Toast / Popover / Modal 互相盖错。

## 可复用库的积累机制

```
ui/
├── tokens/           # 设计令牌单源（生成 CSS vars + TS）
├── components/       # 每组件：源码 + 组件卡 + 测试 + 示例
├── native/           # 原生桥接统一 API
├── icons/            # 图标单源
└── docs/             # 组件目录登记表 + 决策记录 + 引擎基线文档
```

- **入库四件套**（缺一不入）：组件卡、三引擎渲染冒烟（截图对比）、交互 + a11y 测试、可运行示例。
- **查重规则**：新建组件前先查目录登记表；相似组件先扩展后新建；「两个项目各写了一次的」按三次规则提升入库。
- **回流纪律**：项目内的组件改动必须回流上游库；禁止 fork 后静默修改——那是分裂的开始。消费端按 semver 升级并记录。
- **跨项目消费方式二选一并记录**：整体复制（与 guides/ 同哲学，最简单）或 npm workspace / 私有 registry（适合多项目并行）。选定后写进库的 README。
- **弃用流程**：组件目录登记表标注 稳定 / 实验 / 弃用；弃用组件给迁移说明，不直接删除。

## 先设计测试矩阵，再开始建库

| 维度 | 要覆盖的情况 |
|---|---|
| 引擎 | 三引擎渲染快照对比；新 CSS 特性入库前核查记录 |
| 交互 | 每组件键盘全路径；焦点循环；浮层开关 |
| 状态 | 状态矩阵逐格（含暗色 / RTL / 缩放） |
| 输入 | 输入类组件 × 目标 IME 组合态（→ 国际化方案） |
| 桥接 | 每个桥接组件在三平台的行为与降级路径 |
| 回归 | 每里程碑库整体回归；引擎基线变更时全量重跑 |

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 两平台观感不同 | 组件写死色值 / 字体 / 尺寸 | 令牌纪律 + 裸值扫描 |
| 某引擎上组件损坏 | 未过基线核查的 CSS 特性 | 三引擎核查 + 快照对比 |
| 快捷键互相打架 | 组件各自监听键盘事件 | 快捷键注册中心 |
| 输入框打字丢字 | 组合态被组件改值 | IME 纪律进输入类组件卡 |
| 对话框风格突兀 | 该原生的做了 Web 模拟（或反之） | 判定规则 + 平台尊重清单 |
| 复制图片失败 | 剪贴板三引擎差异未封装 | 桥接层统一 API |
| 暗色模式漏网 | 裸色值散落 | 令牌审计进 CI |
| 浮层互相盖错 | z-index 各写各的 | 层级令牌 |
| 组件越攒越乱、两处各一份 | 无登记表、无查重、fork 不回流 | 积累机制四件套 |

以上是常见方向，具体根因必须依据项目代码、引擎版本和实际复现确认。

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先给出令牌单源与横切体系（焦点、快捷键注册、浮层层级），再建组件；组件样式只允许引用令牌，裸值不入库；修饰键用令牌不硬编码；自绘 / 原生按判定规则，平台分支只许存在于桥接层；组件文案一律走语言包，布局用逻辑属性；输入类组件遵守 IME 组合态纪律；每个组件交付组件卡（状态矩阵 + 键盘表 + 平台尊重点 + 引擎差异 + a11y 语义）并登记进目录；新 CSS 特性先过三引擎核查；CSS-in-JS 选型先过 CSP。不得绕过目录登记新建相似组件，不得 fork 修改不回流。实现后补三引擎快照、键盘走查与 IME 测试，并明确列出未覆盖的组合。

方案确认后再改代码；任何引擎行为与预期不符（尤其 WebKitGTK 渲染差异），先在锁定版本上核实并报告，再决定修正或登记为已知差异。

## 五档定位

- **一档**：一致性定义、判定规则、平台尊重清单、令牌单源选型、消费方式决策。
- **二档**：横切体系（焦点 / 快捷键 / 浮层层级）+ 首批核心组件（输入、反馈、桥接层）过四件套。
- **三档**：全量组件补齐、暗色 / RTL / 缩放矩阵、IME 全测。
- **持续**：组件目录随项目积累回流；引擎基线随 Linux 基线升级重跑。
