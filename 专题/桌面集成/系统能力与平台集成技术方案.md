# 系统能力与平台集成：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把应用「向操作系统伸手」的能力——通知、剪贴板、打印、全局快捷键、文件拖放、屏幕捕获、深色模式监听、注册类能力（开机自启、默认应用）——放在一起考虑，避免功能分别做完后才发现：统一 API 只给了最小公分母、能力在关键路径上才发现平台不支持、权限前置缺失导致发布日翻车（macOS 签名 + Bundle ID + 用户授权）、能力不可用时没有任何降级。

它不是某个应用的实现说明，也不预设产品名、框架或能力清单。每个项目都应先按自己的功能需求和目标平台核实能力，再填写自己的决策。

这类问题的共同名字叫「能力假设未验证」。它们几乎从不来自某一个 bug，而来自一个结构：**默认统一 API 全平台等价、默认系统能力无前置条件、默认被拒绝只是异常分支**。本方案的目标是让每项能力先过一遍能力矩阵，再写代码。

两个边界先说清：
- 托盘 / 图标 / 桌面身份 →《托盘技术方案》；窗口几何与焦点 →《窗口与多窗口技术方案》；输入法与键盘输入 →《国际化与输入技术方案》。本方案管其余系统能力的盘点、能力矩阵与降级。
- 权限与暴露面纪律 →《安全边界与权限技术方案》；本方案的能力前置条件（签名、授权）与其发布门禁衔接。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先查清项目、目标平台和锁定的框架版本，并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。

1. **能力清单**是什么？逐项标注「关键路径 / 增强」：关键路径能力不可用时功能残废，增强能力可静默缺失。
2. 框架**统一 API 每项支持到什么程度**？哪些必须平台特定实现（Go 侧）？
3. 每项能力的**平台前置条件**（签名、Bundle ID、用户授权、系统版本、运行时）验证过吗？
4. 能力**不可用 / 被拒绝**时的降级路径是什么？（通知被拒后用户还能从哪里获得同样信息？快捷键被占用时的备选？）
5. **权限请求时机**与文案：启动即请求还是场景触发？被拒绝后的再引导入口在哪？
6. **全局快捷键**：各平台的仲裁行为（Wayland 由合成器仲裁、Windows/X11 被占用即失败、macOS 可能多应用同时响应）核实过吗？注册失败的备选是什么？
7. **深色模式**：是订阅变化事件，还是只读了一次初始值？旧系统上暗色标题栏等行为的回退？
8. **打印**：目标平台原生打印可用吗？不可用时的替代路径（导出 PDF）？
9. **屏幕捕获**：各平台权限模型（macOS TCC 屏幕录制）核实过吗？拒绝后的用户提示？
10. **注册类能力**（开机自启、默认应用、文件关联）：需要哪些？注册与卸载清理是否成对？
11. **测试**：哪些能力可以自动化，哪些必须目标平台手工验收（几乎全部）？

交付给 AI 的设计结果应包含：能力矩阵（能力 × 平台 × 支持级别 × 前置条件 × 降级档位）、关键路径标注、权限时机与文案、测试矩阵。

## 能力矩阵是唯一事实

| 能力 | Windows | macOS | Linux | 统一 API 覆盖 | 前置条件 | 降级档位 |
|---|---|---|---|---|---|---|
| （逐项填写） | | | | 完整 / 部分 / 无 | 签名 / 授权 / 版本 | 完整 / 有限 / 静默缺失 |

矩阵的纪律：

- **先查矩阵再写代码**：任何「待验证」的能力不上关键路径；关键路径能力必须有已验证的可用性证据或已验证的降级。
- **统一 API 是最小公分母**：跨平台框架的统一能力层通常只覆盖最通用的子集（典型如剪贴板只有文本）；高级能力（图片、文件、富内容）默认要平台特定实现，写代码前按矩阵核实，不按希望编码。
- **关键路径 / 增强逐项标注**：增强能力可以静默缺失，关键路径能力不可用就是事故——两者的投入和验收标准完全不同。
- **矩阵只增不漏**：新增系统能力先进矩阵评审（补齐前置条件与降级档），再进代码。

## 权限与前置条件

- **macOS**：通知要求有效签名 + Bundle ID 且经用户授权；屏幕录制、辅助功能走 TCC；请求时机（启动即要 vs 场景触发）立项时定，影响用户信任与通过率。
- **Windows**：通知受聚焦助手 / 勿扰模式影响；WebView2 运行时是通知等能力的前置（→《签名打包与更新分发技术方案》运行时契约）。
- **Linux**：桌面环境差异最大——通知守护进程可能不存在，全局快捷键由合成器 / 桌面环境仲裁，托盘宿主可能缺失（→ 托盘方案）。
- **被拒绝是常态分支，不是错误分支**：每项需授权的能力都要有「拒绝后世界照常运转」的设计——替代入口、再引导说明、功能降级，而不是弹一个报错了事。

## 降级的三档

每项能力预先选档写进矩阵，不许「到时候再说」：

- **完整能力**：全平台可用。
- **有限能力**：部分平台或部分条件下可用；降级时明确告知 + 提供替代入口（如打印不可用 → 导出 PDF）。
- **静默缺失**：仅增强项允许；缺失不影响任何关键路径。

「不可用就报错」不是降级设计。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 发布日通知不弹 | macOS 未签名 / 无 Bundle ID / 未授权 | 前置条件进发布门禁 + 真机冒烟 |
| 快捷键时灵时不灵 | 平台仲裁差异未验证、无失败备选 | 平台契约 + 注册失败备选 |
| 深色模式切了没反应 | 只读初始值、未订阅事件 | 事件订阅 + 旧系统回退 |
| 剪贴板贴不了图片 | 统一 API 公分母假设 | 能力矩阵 + 平台特定实现 |
| 打印按钮无效 | 原生打印不可用、无替代 | 降级路径（导出 PDF） |
| 截屏一片黑 | TCC 未授权、无引导 | 权限时机 + 再引导入口 |
| 卸载后自启动残留 | 注册类能力无清理 | 注册 / 清理成对 |
| Linux 上功能集体异常 | 桌面环境差异未验证 | 目标环境逐项冒烟 |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| 能力 × 平台 | 每项能力在每个目标平台：可用、前置缺失、用户拒绝、系统版本回退 |
| 关键路径 | 关键路径能力在目标最低环境验证可用性 |
| 拒绝 | 每项授权能力的拒绝路径与再引导 |
| 注册类 | 注册生效、重复注册、卸载清理 |
| 组合 | 勿扰模式 / 焦点模式下的通知、多屏 / 锁定会话下的行为 |

每次验收记录：平台、前置条件状态、能力实际表现、降级路径是否走通。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先给出能力矩阵（能力 × 平台 × 支持级别 × 前置条件 × 降级档位）并逐项验证前置条件、给出证据。统一 API 覆盖不到的能力显式标注需平台实现，不得按希望编码；关键路径能力必须有已验证可用性或已验证降级；权限请求时机与文案立项确认，被拒绝有再引导与替代入口；注册类能力注册与清理成对；降级档位逐项预先选定，「不可用就报错」不算降级。平台相关行为先在目标环境验证，未验证标注“待验证”。实现后补各能力在目标平台的冒烟测试与拒绝场景测试，并明确列出未覆盖的组合。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位（与主大纲的衔接）

- **一档**：能力清单与关键性标注（大纲准入条目集中在二 / 三档；关键路径能力一档即登记）。
- **二档**：能力矩阵与前置条件验证（衔接主大纲「托盘平台降级」等条目）。
- **三档**：降级全量、权限时机（对应主大纲「通知的平台前置条件」「打印能力」「全局快捷键平台契约」「文件拖放」「屏幕捕获」「深色模式监听」各条）。
