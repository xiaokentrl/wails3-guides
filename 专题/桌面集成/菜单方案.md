# 菜单：Wails3 + Go 专用方案

## 这份方案是做什么的

桌面应用的「菜单」不是一个组件，是**一组渲染面**：应用菜单栏（macOS 原生菜单栏 / Win-Linux 顶层菜单）、托盘右键菜单、界面右键上下文菜单、命令面板（⌘K），以及挂在菜单项上的快捷键。本方案把它们收进**一份命令注册表、多个渲染面**的结构里，避免经典错位：菜单灰了快捷键还能按、命令面板里缺项、右键菜单和应用菜单行为不一致、改了快捷键只改了一处。

**硬性目标：新增一个命令 = 在命令注册表登记一次**——它的菜单位置、快捷键、可用条件、处理函数、出现在哪些渲染面，全部随登记生效；任何渲染面不单独维护命令清单。

边界先说清：托盘宿主行为、双击语义、图标与身份 →《托盘技术方案》（本方案只管托盘菜单的**定义与本地化**）；全局快捷键的平台仲裁 →《系统能力与平台集成技术方案》；命令面板与右键菜单的组件实现 →《多平台一致组件库方案》；菜单文案 →《多语言实现方案》。

## 核心：命令注册表是唯一事实

```go
// app/menu/ —— 命令单源（→ 后端目录结构方案）
type Command struct {
    ID        string        // "library.import" —— 稳定 ID，永不改名（日志/遥测引用它）
    LabelKey  string        // i18n 键，文案走语言包
    Shortcut  string        // "Mod+O" —— Mod 是修饰键令牌（macOS=Cmd，其余=Ctrl）
    Surfaces  []Surface     // MenuBar / ContextMenu / Palette / Tray —— 出现在哪些面
    Handler   Handler       // Go 侧命令（绑定 ID）或前端动作 ID——位置显式声明
    When      StateFunc     // enabled / checked 派生自事实（同步层读数），不各自维护布尔
    Section   string        // 菜单分区与排序
    Role      Role          // 标准角色项（see 下文），非自定义命令
}

type Registry interface {
    Register(cmds ...Command)          // 启动期一次注册，运行期不改结构
    Resolve(id string) (Command, bool) // 全渲染面按 ID 取命令
}
```

三条纪律：

1. **命令是唯一事实，菜单是它的视图**。按钮、快捷键、菜单项、面板项全部调用同一个命令 ID；「按钮能点但菜单是灰的」这类错位在结构上不可能出现——因为它们是同一份数据。
2. **可用状态派生自事实**（`When` 读同步层的领域状态），不散落布尔开关；状态变化 → 菜单刷新走节流（→ 性能方案事件预算），原生菜单的刷新机制按锁定版本**待验证**（不支持热更新则重启生效并声明）。
3. **快捷键由注册表统一发放**：菜单项声明的快捷键自动进入前端快捷键注册中心（→ 组件库方案横切体系）；重复快捷键在注册期即报错；组合态冲突规则 → 国际化方案；注册表之外不得有第二处快捷键定义（全局快捷键除外，单列且标注 → 系统能力方案）。
4. **命令 ID 的权威在领域层**：稳定 ID 由领域命令清单定义（→《后端目录结构方案》`domains/`），菜单注册表、快捷键绑定、权限声明（→《登录与权限方案》的命令↔权限映射）全部引用同一 ID——命令的语义只登记一次，各渲染面零发明；同一命令 ID 在两处定义即构建错误。

## 三层渲染面，各自适配

| 渲染面 | 渲染方式 | 适配要点 |
|---|---|---|
| 应用菜单栏 | **原生**：macOS 原生菜单栏（缺席即残缺）；Windows/Linux 顶层原生菜单或应用内自绘菜单栏——二选一登记进平台尊重清单 | 由 Go 侧从注册表渲染；`Surfaces` 含 MenuBar 的命令才出现 |
| 托盘菜单 | 原生（→ 托盘方案） | 同一份注册表，`Traces` 面过滤；宿主缺失降级 → 托盘方案 |
| 右键上下文菜单 | **Web 自绘**（→ 组件库方案：工作流交互走 Web 保一致） | 前端经只读绑定取注册表（过滤 `ContextMenu` 面 + 当前上下文），渲染统一组件 |
| 命令面板 | Web 自绘 | 同上，取全量命令（含不在菜单显示但可执行的），搜索与最近使用由面板组件管 |

**前端如何拿到定义**：注册表经只读绑定序列化给前端（→ 安全方案：只读分类）；前端不维护任何命令清单副本——它拿到的是投影，不是第二事实源。

## 标准角色与平台约定

- **macOS 必须项**：App 菜单（About / Settings / Quit 走标准角色，位置符合 HIG）；**Edit 菜单用标准角色**（剪切/拷贝/粘贴/全选）——文本编辑与剪贴板行为依赖标准角色，自定义替代会有隐性缺失（具体范围随锁定版本**待验证**）。
- **标准角色映射**：注册表用 `Role` 字段声明标准项（about / quit / cut / copy / paste / selectAll…），渲染面各自映射到平台原语；标准项不走自定义 Handler。
- **Windows/Linux 约定**：文件/编辑/视图/帮助的分区顺序遵循平台惯例；Alt 加速键可选（决策记录）。

## 本地化与重建

- 菜单文案全部经 `LabelKey` 走语言包（Go 侧 `T()`）；语言切换 → 菜单**重建**联动（→ 多语言方案联动表）：运行时重建即时生效，框架不支持则重启生效并写明降级——**待验证**项随锁定版本验证。
- RTL：原生菜单多数无法镜像方向，降级已在国际化方案立项时选定；Web 自绘菜单遵循逻辑属性。

## 目录落位

```
app/menu/            # 命令注册表（单源）：命令定义、标准角色、Surfaces 声明
internal/platform/   # 各渲染面的原生适配（菜单栏构建、托盘菜单构建，构建标签分文件）
internal/binding/    # 只读暴露：注册表投影给前端；命令分发（Go 侧 Handler 的写入口）
frontend/…/commands/ # 快捷键注册中心消费注册表；命令面板与自绘菜单的取数
```

依赖方向：`platform/` 与 `binding/` 读注册表，注册表不依赖渲染面；前端只读消费。

## 验收清单

- [ ] 新增命令演练：登记一次 → 应用菜单、托盘菜单、右键、面板、快捷键按 `Surfaces` 全部出现（不出现者也符合声明）
- [ ] 可用状态：事实变化 → 菜单灰/亮与快捷键、面板、按钮同步（同一 `When`）
- [ ] 重复快捷键注册被拒绝；修饰键随平台（Cmd/Ctrl）正确
- [ ] macOS：App 菜单与 Edit 标准角色齐备；剪贴板四件套在 WebView 内可用
- [ ] 语言切换：菜单文案按联动表生效（重建或重启降级，已声明）
- [ ] 右键菜单在混合 DPI / 缩放档位下定位正确（→ 组件库方案浮层）
- [ ] 命令执行有日志（命令 ID 进日志，→ 可诊断性方案关联 ID）
- [ ] 托盘菜单在宿主缺失时降级路径走通（→ 托盘方案）

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 菜单灰了快捷键还能按（或反之） | 快捷键与菜单各管各的状态 | 命令单源 + `When` 派生 |
| 面板里缺命令 | 面板单独维护清单 | 全渲染面读注册表 |
| 改快捷键漏了一处 | 多处定义 | 注册表唯一发放，重复即报错 |
| macOS 文本操作时灵时不灵 | Edit 菜单用自定义项替代标准角色 | 标准角色映射 |
| 切语言菜单没变 | 菜单不在语言联动表 | 联动表含菜单重建（→ 多语言方案） |
| 菜单状态刷新迟滞或风暴 | 每次事实变化全量重建菜单 | `When` 派生 + 节流刷新 |
| 右键菜单位置飘 | 自绘菜单各写各的定位 | 统一浮层组件（→ 组件库方案） |
| 命令执行无处可查 | 无命令 ID 日志 | 执行日志带命令 ID + 关联 ID |

## 给 AI 的实施约束模板

开始实现时，可要求 AI：

> 先建命令注册表（ID / LabelKey / Shortcut / Surfaces / Handler / When / Role），全部渲染面只读消费它——不得在任何渲染面单独维护命令清单或快捷键定义；快捷键由注册表统一发放并查重，修饰键用令牌；命令可用状态由 `When` 从事实派生，刷新走节流；标准角色映射到平台原语，macOS App 菜单与 Edit 角色齐备；文案全走语言包，语言切换按联动表重建并声明降级；前端经只读绑定取注册表投影，不持有第二清单。菜单运行时重建、标准角色覆盖范围等按锁定版本验证，未验证标注待验证。实现后跑验收清单，并明确列出未覆盖的渲染面组合。

方案确认后再改代码；菜单能力与框架版本冲突时（如运行时重建不支持），先报告差异并等待裁决。
