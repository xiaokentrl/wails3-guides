# 无障碍与辅助使用：通用规划方案

## 这份方案是做什么的

这是一份给新项目立项、选框架和让 AI 开始写代码前使用的通用规划指南。它把键盘可达、屏幕阅读器、焦点、对比度、缩放放在一起考虑，避免功能做完后才发现：功能只有鼠标一条路径、屏幕阅读器用户拿不到任何信息、焦点进得去出不来、系统缩放下布局崩坏。

**投入档位先决**：是否全面投入取决于目标用户（主大纲三档「无障碍基础」的准入问题）。目标用户含辅助技术用户、或有合规要求（政府采购、行业规范）时，本方案为完整纪律；否则可整项按五档暂缓，但必须写下触发重新评估的条件——键盘可达这类地基后补成本极高，暂缓前先做一档的键盘完备盘点。

它不是某个应用的实现说明，也不预设产品名、框架或合规标准。每个项目都应先按目标用户和锁定的框架版本核实能力，再填写自己的决策。

这类问题的共同名字叫「无障碍被当成最后刷漆」。它们几乎从不来自某一个 bug，而来自一个结构：**键盘与语义的地基没有先打，后补时等于重写交互**。本方案的目标是把地基放进一档。

两个边界先说清：
- 输入法与键盘输入的组合态行为 →《国际化与输入技术方案》；模态焦点陷阱的窗口行为 →《窗口与多窗口技术方案》。
- 权限前置（macOS 辅助功能 TCC）→《系统能力与平台集成技术方案》。

## 开始写代码前，先让 AI 回答这些问题

要求 AI 先查清项目、目标用户和锁定的框架版本，并给出证据；没有查证的行为要标为“待验证”，不能把猜测当事实。

1. **目标用户**是否包含辅助技术（屏幕阅读器、开关控制、语音输入）用户？有合规要求吗（采购、行业、地区法规）？投入档位是什么？
2. **键盘完备性**：每个功能是否有键盘路径？焦点顺序与视觉顺序一致吗？模态焦点陷阱有进出口吗？
3. **语义标注**：控件是否具备角色 / 名称 / 状态三件套？WebView 中原生控件与自绘控件的语义差异验证过吗？
4. **屏幕阅读器**：目标平台各用什么验证（Windows Narrator / NVDA / JAWS，macOS VoiceOver，Linux Orca）？谁验、验哪些流程？
5. **缩放与 DPI**：系统 125% / 150% / 200% 缩放下布局如何？应用内字体缩放支持吗？与窗口几何的 DIP 策略衔接了吗？
6. **对比度与深色模式**：文本对比度达什么等级？状态是否不只靠颜色区分？
7. **动效**：是否尊重系统「减少动态效果」设置？有闪烁内容吗？
8. **平台已知限制**：Linux 上 WebView 激活不自动获得焦点、读屏需用户手动点击（主大纲已列）验证过吗？macOS 辅助功能 TCC 前置核实了吗？
9. **验收**：键盘走查清单、读屏脚本、对比度检测，各自怎么跑、多久跑一次？

交付给 AI 的设计结果应包含：目标用户与合规声明、键盘可达清单、语义标注规则、读屏验收脚本、缩放与对比度矩阵。

## 键盘优先

- **键盘路径是可达性的地基**：逐功能列键盘路径，纯指针交互（拖拽、右键菜单、悬浮）必须有等价键盘或菜单路径。
- **焦点纪律**：焦点顺序与视觉顺序一致；模态有焦点陷阱且 Escape 可出、关闭后焦点归还（→ 窗口方案模态规则）；焦点指示可见——去掉默认描边必须提供替代。
- **快捷键体系成文**：应用内快捷键与全局快捷键分开登记（全局键的平台仲裁 → 系统能力方案；组合态冲突规则 → 国际化方案）。

## 语义与读屏

- **语义三件套在立项定规则**：每个控件的角色 / 名称 / 状态可被辅助技术读取；动态区域（进度、通知、结果反馈）用对应语义，读屏才能自动播报。
- **自绘控件是语义黑洞**：优先用带原生语义的控件；必须自绘时，语义补全与读屏验证是验收的一部分，不是可选美化。
- **逐平台验证目标读屏器**：每平台的系统默认读屏加常用第三方，关键流程做「只靠耳朵走通」的脚本化走查。

## 缩放、对比与动效

- **缩放档位进测试矩阵**：系统缩放与应用内字体缩放分别验证；布局与窗口几何按 DIP 策略衔接（→ 窗口方案）。
- **状态不只靠颜色**：成功 / 警告 / 失败要有颜色之外的第二通道（图标、文字、形状）；文本对比度按合规声明选定的等级检测。
- **动效尊重系统设置**：提供减少动态效果的跟随；无超阈值闪烁。

## 常见根因

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 读屏用户完全不可用 | 自绘控件无语义 | 语义三件套规则 + 原生控件优先 |
| 模态关不掉、焦点丢失 | 陷阱无出口、关闭后焦点不归还 | 模态规则（→ 窗口方案） |
| 键盘用户到不了某功能 | 只有指针路径 | 键盘完备清单逐功能核对 |
| 缩放后布局崩坏 | 固定像素布局、未测缩放档 | 缩放矩阵进测试 |
| 状态分不清 | 只用颜色区分 | 颜色之外的第二通道 |
| Linux 读屏拿不到焦点 | 平台已知限制未验证 | 目标环境验证 + 用户引导文案 |
| 快捷键与输入法打架 | 组合态规则缺失 | 组合态快捷键规则（→ 国际化方案） |

以上是常见方向，具体根因必须依据项目代码、框架版本和实际复现确认。

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖的情况 |
|---|---|
| 键盘 | 全功能键盘走查、焦点顺序、陷阱进出与归还 |
| 读屏 | 每平台目标读屏器跑关键流程（含动态播报） |
| 缩放 | 各系统缩放档位、应用内字体缩放、混合 DPI |
| 对比 | 主题 × 状态组合的对比度检测 |
| 平台 | Linux 焦点限制、macOS TCC 前置、各读屏器差异 |

每次验收记录：读屏器与版本、走查流程、实际播报内容。未测的组合标为未验。

## 给 AI 的实施约束模板

开始此类任务时，可要求 AI：

> 先确认目标用户与合规声明、给出投入档位。全部功能提供键盘路径并维护键盘完备清单；模态焦点陷阱有进出与归还（→ 窗口方案）；控件语义（角色 / 名称 / 状态）按立项规则实现，自绘控件必须有语义补全并列入读屏验收；缩放档位进测试矩阵；状态不只靠颜色；动效尊重系统减少动态设置；平台已知限制（Linux 读屏焦点、macOS TCC）先验证再依赖，未验证标注“待验证”。实现后补键盘走查与目标读屏器的验收记录，并明确列出未覆盖的组合。

方案确认后再改代码；任何行为与产品需求、框架能力或平台限制冲突时，先报告差异并等待裁决。

## 五档定位（与主大纲的衔接）

- **一档**：目标用户与合规声明（决定投入档位）、键盘完备盘点。
- **三档**：键盘完备、语义规则、缩放矩阵（对应主大纲「无障碍基础」「模态焦点管理」条目）。
- **五档**：目标用户不含辅助技术用户时，可整项暂缓并记录触发条件（进入辅助用户需求或合规要求时重新评估）。
