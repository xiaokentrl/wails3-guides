# 目录树双确认门方案：通用规划方案

## 这份方案是做什么的

新项目**写第一行代码之前**，AI 必须产出两棵完整的目录/文件结构树并交用户确认；用户明确同意后，才允许进入下一步。两棵树：

1. **开发树**——项目目录的结构树，含已规划的文件（规划中、尚未创建的文件也要列出并标注状态）；
2. **安装终态树**——安装包在三平台**全新安装后**磁盘上的最终全部目录与文件树：程序区、数据区、配置文件、缓存、日志、快捷方式、`.desktop`/`.lnk`、安装器自产物（manifest、目录结构.txt 等），**含一切隐藏文件**——凡是安装动作直接或间接落到磁盘上的，一个不漏。

母法与分工：《默认安装目录规划方案》定目录契约（六类文件 × 三平台唯一归属）与**安装期**预览门禁（安装器向导里确认树）；本方案把确认门**提前到动工前**——安装期门禁确认的是实现，动工门禁确认的是规划，两道门用的必须是同一棵树；《后端目录结构方案》《前端目录结构方案》定开发树的内部组织；《立项范围与决策记录方案》定确认记录怎么留痕（确认过的树是 ADR 级产物，改动走变更控制）。

**为什么必须在写码前**：目录结构是后补极贵的决策之一——代码一旦落盘，「文件该住哪」就从规划问题变成迁移问题（迁移 = 全部路径引用重写 + 用户数据搬家 + 卸载逻辑重写）。先确认树再写码，把「到处拉屎」消灭在产生之前，而不是事后清理。

## 硬性目标

1. **无确认树，不写码**：两棵树未经用户逐节点确认，禁止创建任何项目文件（含脚手架与 `.gitignore`）；
2. **最小侵占**：安装终态树每个节点都必须举证「为什么必须在、谁创建、谁清理」——没有理由的节点就是拉屎候选，删掉；三平台用户磁盘上的新增顶层目录数有显式预算并写进方案；
3. **两树可互溯**：开发树的每个产物能映射到安装终态树的落点；安装终态树每个文件能溯源到「开发树哪个产物 / 安装器哪一步 / 运行期哪段代码」——映射不上的节点不通过。

## 一、两棵树长什么样

### 开发树（仓库形态）

- 从仓库根开始画到文件级；**已规划的文件**与已存在的文件并列，状态标注：`[存在]` / `[规划]` / `[生成]`（构建生成物，不入库）；
- 生成物目录（`dist/`、`build/bin/`）单列一节并注明「不入库、安装树从它取件」；
- 与《后端/前端目录结构方案》的守门清单互验：结构先过那两份方案的清单，再走本方案确认——确认门不做结构评审，只做授权。

### 安装终态树（交付形态）

按平台各画一棵（或契约相同则一棵 + 差异注记），逐节点标注四列：**路径 / 类别（程序|配置|数据|缓存|日志|安装器自产物）/ 创建者（安装器|应用首启|运行期）/ 卸载处置（删|保留|用户选择）**：

- **配置与隐藏文件单列成节**，逐个列名——它们最容易漏（`.desktop`、开始菜单 `.lnk`、`~/Library/Preferences/<bundle>.plist`、Windows 注册表白名单键（若 opt-in）、应用首次启动生成的默认配置文件、运行期锁文件）；
- **运行期长出来的文件也算**：首次启动会创建什么（默认配置、数据库、缓存目录），动工前就要写明——「首启创建清单」是安装终态树的附表，不写就是运行期拉屎的敞口；
- 安装器自产物（manifest、`目录结构.txt`、`install-info.ini`）在列——它们也是磁盘占用（→《默认安装目录规划方案》所写即所录）。

### 可指定安装根时：确认的是参数化树规则，不是固定路径快照

Windows 的程序根由用户指定（解析链第 1 级 = 用户指定绝对遵从，→《默认安装目录规划方案》；NSIS `MUI_PAGE_DIRECTORY` 已实装），Linux per-user/system 两档同理。根可变时，确认门的产物是**树模板**而非一棵死树：

1. **确认三要素**：默认安装根的树（解析链求值结果）+ 用户可改的范围与边界（哪些节点跟着根走、哪些固定在契约位置——数据区契约模式不随程序根移动）+ 改根后树的**推导规则**（用户改到 `E:\工具\我的软件`，树逐节点如何重排）；
2. **确认快照 = 模板 + 默认根实装样张**：立项包存树模板与默认根下的实装样张各一份；
3. **实装对照跑两个场景**：默认根安装 diff = 样张；**用户自定义根安装 diff = 按推导规则重排的树**——只测默认根，等于没测「用户能指定」这条能力；
4. **防呆进推导规则**：用户选了无写权限/只读/系统保护区路径 → 预览树即时标红禁用下一步（安装期门禁同规），动工前就把「非法根的树长什么样」写清楚。

## 二、最小侵占原则（反拉屎判定）

每个节点过三问，答不上来就删：

1. **为什么必须在**：删掉它功能坏吗？「可能有用来」不行（→ 写少阶梯第 1 级）；
2. **谁创建**：安装器、首启、还是运行期某段代码？写不出创建者的节点不通过；
3. **谁清理**：卸载时删还是保留？升级时会被覆盖还是残留？「没想过」不通过。

**数量预算**（写进方案，超预算即重新设计）：全新安装后，用户磁盘上**新增的顶层目录数**有上限（如 Windows 用户目录下新增 ≤ 2 个契约目录、`%APPDATA%`/`%LOCALAPPDATA%` 下各 ≤ 1 个应用目录）；聚合模式下程序区一棵树打包全部。预算迫使设计先聚合再展开，而不是先散落再辩护。

**拉屎红旗清单**（见到即打回）：

| 红旗 | 正确归属 |
|---|---|
| exe / .app 旁边出现 ini / log / 数据文件 | 配置/数据/日志进契约目录（macOS 签名直接拒启） |
| `$HOME` 裸扔 dotfile（`~/.我的软件`） | 按平台契约目录，不占 HOME 根 |
| 缓存写进配置目录、日志混进数据目录 | 六类分目录，卸载语义靠它区分 |
| 桌面/开始菜单快捷方式未在树中登记、卸载残留 | 快捷方式是安装终态树节点，卸载处置必须写明 |
| 升级后旧版本目录残留（`app-1.0/`、`app-1.1/` 并存） | 升级路径单列：旧目录谁删、何时删 |
| 临时文件写死路径（`/tmp` 之外的「临时」目录） | 临时类进系统临时目录或应用缓存目录，退出/卸载必清 |

## 三、确认流程（门怎么过）

```
AI 产出两棵树（开发树 + 各平台安装终态树 + 首启创建清单）
  → 逐节点标注四列（路径/类别/创建者/卸载处置）+ 最小侵占自查（三问全过）
  → 提交用户：逐节点确认或调整（调整记录进变更列表）
  → 用户明确同意 → 确认记录留痕（树快照存入立项包，进决策日志/ADR）
  → 才允许写第一行代码
```

纪律：

1. **「未提出异议」不是同意**——用户必须显式确认（「可以」「同意」或逐节点回复），AI 不得把沉默当授权自行开工；
2. **树是快照不是邮件**：确认过的树存入立项包（`docs/` 或决策记录约定位置），后续改动**先改树、走变更控制、再改代码**（与「需求变更先改验收标准再改实现」同构）；
3. **中途新增文件**也要回门：开发期冒出的新文件类型（新缓存格式、新配置文件）补进两棵树并重新确认该节点，不得静默落盘；
4. 与安装期门禁衔接：安装器预览页渲染的树 = 本方案确认过的安装终态树——两道门若对不上，以立项包快照为准，差异按变更处理。

## 四、树的一致性验证（进了 CI 就不是君子协定）

| 验证 | 机制 |
|---|---|
| 开发树 ↔ 安装树映射 | 映射表（产物 → 落点）逐行核对；安装树出现映射表没有的文件 = 构建脚本越权，拦截 |
| 安装器实装对照 | CI 装一次（或 dry-run 产出计划，→ plan-then-apply），`diff` 实际落盘树与确认快照——差异即失败 |
| 首启创建对照 | 干净环境跑一次应用 → 24h 后全盘 diff 预期位置，契约外新增文件 = 拉屎，按缺陷登记 |
| 卸载净空 | 卸载后 diff：除声明保留的数据区外无残留（快捷方式、自产物一并核） |

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 卸载后用户目录一堆残留 | 卸载处置列没写或没执行 | 四列标注 + 卸载后 diff 验证 |
| 「这文件谁创建的」没人知道 | 树里没有创建者列 | 三问不过不通过 |
| 运行一周后配置目录长出一堆没见过的文件 | 首启/运行期写入没规划 | 首启创建清单 + 24h 全盘 diff |
| 两平台行为不一致 | 只画了一棵树 | 按平台各画或差异注记 |
| 树确认了但代码没照做 | 确认无快照、无 CI 对照 | 快照入立项包 + dry-run diff 进 CI |
| 规划外的文件静默出现 | 中途新增不走门 | 新文件类型回门重确认 |
| 用户以为确认过其实没确认 | 沉默被当授权 | 显式确认才开工；AI 不得自行开工 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 门本身 | 未确认两棵树时，AI 是否真的未创建任何文件（抽查立项包时间线 vs 首个提交） |
| 完整性 | 安装终态树含配置/隐藏文件/安装器自产物/首启创建清单四节，缺一退回 |
| 最小侵占 | 每节点三问有答案；顶层目录数在预算内；红旗清单零命中 |
| 互溯 | 开发树每个产物有安装树落点；安装树每个文件有来源；映射表零孤儿 |
| 实装 | 全新安装后 diff = 确认快照；**可指定根平台两个场景各测**（默认根 + 用户自定义根按推导规则重排）；首启 24h diff 无契约外文件；卸载后净空 |
| 指定根 | 非法根（只读/保护区/无空间）预览树标红禁用；合法自定义根落盘与推导规则逐节点一致，无静默重定向 |
| 变更 | 故意新增一个文件类型，确认走回门而不是静默落盘 |

## 给 AI 的实施约束模板

> 新项目写第一行代码前，先产出并提交用户确认两棵树：① 开发树——仓库根到文件级，已存在/规划/生成三种状态标注，生成物单列；② 安装终态树——按平台画，逐节点四列（路径/类别/创建者/卸载处置），配置与隐藏文件、安装器自产物、首启创建清单单列成节；**可指定安装根的平台（Windows 用户指定、Linux per-user/system）确认的是参数化树规则：默认根树 + 可改范围边界 + 改根推导规则，快照=模板+默认根实装样张**。每个节点过最小侵占三问（为什么必须在/谁创建/谁清理），答不出即删；顶层新增目录数写预算；红旗清单（exe 旁 ini、HOME 裸 dotfile、缓存混配置、快捷方式未登记、升级残留、临时文件写死）逐条自查零命中。两树之间做产物→落点映射表，零孤儿。**用户显式同意（沉默不算）后把树快照存入立项包，才允许写码**；后续新增文件类型回门重确认该节点，先改树再改代码。实现后：默认根安装 diff = 样张、用户自定义根安装 diff = 推导规则重排树（两场景都测）、首启 24h 全盘 diff 无契约外文件、卸载净空，全部对照进 CI。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 两棵树的产出与用户确认——**写码前的硬门**，与立项范围方案同为一档前置 |
| 二档 | 映射表 + 安装器实装对照（dry-run diff）进 CI |
| 三档 | 首启 24h 全盘 diff、卸载净空对照、升级路径残留检查 |
| 持续 | 新文件类型回门重确认；平台差异树随框架升级复核 |
