# 立项范围与决策记录方案：通用规划方案

## 这份方案是做什么的

来源：行业 kickoff / 软件发展计划清单的「项目规划、需求、设计与架构」三节（一页范围说明含明确 non-goals、RACI、风险分级、验收标准、ADR、架构评审），以及中文技术方案评审清单里反复出现的四份产物：需求↔设计↔实现追踪矩阵、关键接口清单、安全与合规模板、风险与应对清单。

本库的主大纲已经用五档节奏把「技术准入问题」组织得很好，本方案补的是它之前那一层：**这些问题由谁回答、答案算不算数、改动怎么留痕、哪些决定明确不做**。它管立项治理，不管具体技术结论（各专题为准），不管人员排期与预算数字（由项目决定）。

特别地，本库自己有一条纪律：「暂缓是被记录的决策，不是被遗忘的遗漏」——每条暂缓要有**书面理由 + 触发重新评估的条件**。ADR 与决策日志就是这条纪律在编码前的落点：**如果连「为什么选 Wails3」都没记录，五档里的暂缓理由也迟早会失传**。

不预设：产品形态、团队规模、文档平台、评审周期、模板字段数量。所有具体值由项目决定。

## 开始写代码前，先让 AI 回答这些问题

1. 问题陈述是什么（用户视角 1–3 句）、目标用户是谁、为什么现在做？
2. 一页范围说明里，**明确不做的（non-goals）** 有哪些？逐条写具体，不能只写「其他功能不做」。
3. 成功标准怎么量化（可测指标、采用目标、业务 KPI）？谁在什么时候测？
4. 项目风险分级（规模/合规/数据敏感度）是什么？分级如何决定评审深度（是否必须威胁建模、是否必须架构评审）？
5. RACI：谁负责、谁批准、咨询谁、通知谁？安全、设计、支持是否列入？
6. 每条功能需求的验收标准能否写成 Given/When/Then，让 QA 直接测？
7. 需求↔设计↔实现↔测试的追踪矩阵在哪？矩阵里出现孤儿（无实现的需求 / 无需求的实现）怎么处理？
8. 非功能需求（性能、可用性、合规、可访问性、留存）是否有具体数值与测量方法（→《性能与资源基线技术方案》）？
9. 重大技术选择各有一份 ADR 吗？每份是否写了备选项与被否决理由、状态、触发重评条件？
10. 决策日志：评审结论、责任人、 deadlines 记在哪？聊天记录里的结论如何转成在库文档？
11. 变更控制：范围、接口、性能、数据契约变更走什么模板、谁批准（→《绑定层契约与生成物方案》《数据模型与数据契约方案》）？
12. 风险登记：每条是否有检测信号、影响、应对、owner、复审日期？
13. 暂缓项与主大纲五档如何对接：每条暂缓的理由、触发条件、随版本评审重读的机制在哪？
14. 交付物清单（主大纲附录）由谁维护、何时核对「一档已完成」？

交付给 AI 的设计结果应包含：一页范围说明、需求与验收标准、追踪矩阵、ADR 目录、决策日志、风险登记、变更控制模板、暂缓清单与复审机制。**没有答案的项标「未完成」，不得用「后续补充」当作已完成。**

## 核心纪律

### 一、范围：non-goals 是最常被跳过的一页

| 项 | 要写清 | 验收证据 |
|---|---|---|
| 问题陈述 | 用户视角、目标用户、为什么现在 | 一页说明，含可测成功标准 |
| in-scope | 交付物逐条列举 | 范围清单 |
| **non-goals** | 明确排除的能力、平台、集成、合规范围 | 排除清单逐条具体，且与五档暂缓项互相引用 |
| 成功标准 | 指标 / 目标值 / 测量方法 / 验收阶段 | 一页指标表（→《性能与资源基线技术方案》） |
| 风险分级 | 规模与敏感度决定评审深度 | 分级结论 + 是否触发威胁建模/架构评审 |
| RACI | 负责/批准/咨询/通知 | 名单与职责，无「大家一起负责」 |

**「暂缓」与「non-goal」不是同义词**：non-goal 是当前不做且没打算做；暂缓是明确要做、只是排到后面，必须带触发条件。混写会让未来的自己分不清「故意没做」和「忘了做」。

### 二、需求：验收标准先于实现

- 每条需求有 Given/When/Then 验收标准；「满足需求」「尽量快」这类不可测表述退回重写。
- 追踪矩阵四列：需求 ID → 设计/ADR → 实现位置 → 测试用例。任一列为空即标债，带 owner 与截止日。
- 需求变更走同一张矩阵：先改需求与验收标准，再改设计与实现；禁止「代码先改、文档后追」。
- 非功能需求与功能需求同等对待：性能、可用性、合规、可访问性、留存都要有数值与测量方法，不能只在发布前口头补。

### 三、ADR：每个重大选择一份，含被否决的理由

| 字段 | 要求 |
|---|---|
| 标题与编号 | 一个决策一份，不把三个决策塞进一篇 |
| 状态 | proposed / accepted / superseded（被替代时指向新 ADR，不删旧文） |
| 背景与约束 | 当时的平台基线、法规、团队能力，写清时间 |
| 备选项 | ≥2 个，每个写适用条件与代价 |
| 决定与理由 | 为什么选它，**以及为什么否决其他** |
| 后果 | 引入的债、需要新增的门、受影响的专题 |
| 触发重评条件 | 什么变化会让这个决定失效（框架升级、新平台、合规要求、首个企业客户） |

必须成文的选择（起点清单）：框架与版本锁定、数据存储与驱动、API/绑定契约风格、同步模型、前端框架与状态管理、打包与分发渠道、目标语言范围、身份与目录契约、测试分层。**ADR 不是事后补的说明书**：决定做出时写，哪怕只有半页；事后回忆写出来的「理由」通常只是对结果的合理化。

### 四、决策日志、风险登记与变更控制

- 决策日志逐条记：议题、结论、责任人、日期、关联 ADR/需求 ID。聊天/会议里的结论必须转成在库条目，否则不可追溯。
- 风险登记每条有：描述、检测信号（怎么知道它发生了）、影响、应对、owner、复审日期。「风险低」不是一条记录。
- 变更控制模板覆盖四类变更：范围、接口/契约、性能指标、数据 schema。每类写明评审人与门（→《CI矩阵与质量门禁方案》）。
- 架构评审读 ADR 与威胁模型，目标是暴露爆炸半径与隐藏耦合，不是讨论代码风格；结论与未决问题书面留档。

### 五、与主大纲五档对接

| 五档 | 治理动作 |
|---|---|
| 一档 | 逐项回答「核心问题 → 验收证据」，答案指向 ADR/专题；任一项无答案 → 不写业务代码 |
| 二档 | 可分发里程碑评审：追踪矩阵无孤儿、必需门全绿、暂缓项逐条有理由与触发条件 |
| 三档 | 带债进 MVP 的每一笔登记 owner 与偿还节点，随版本评审重读 |
| 四档 | 公开发布前：合规/安全/发布门逐项核销，未验项明确列出（→《发布交付流水线方案》） |
| 五档 | 暂缓清单随每次版本评审重读；触发条件达成即转立项，不得静默过期 |

**裁剪是被记录的决策**：本方案要求所有「暂缓」「不做」「未验」都能查到当时的理由，这与《托盘技术方案》里「修复没生效」的教训同源——**没有记录的决定，等于没有决定**。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 范围越做越大、工期失控 | 没写 non-goals、变更无模板 | 一页范围说明含排除清单 + 变更控制门 |
| 半年后没人说得清为什么选这个框架 | 决策只在聊天记录里 | 每个重大选择一份 ADR，含被否决理由 |
| 验收时扯皮「这算不算做完」 | 验收标准写成「满足需求」 | Given/When/Then + 可测指标 |
| 上线后发现某需求没人实现 | 没有追踪矩阵 | 四列矩阵 + 孤儿检查 + owner |
| 框架升级时不知道哪些结论失效 | ADR 没写触发重评条件 | 每份 ADR 带触发条件，升级即复核 |
| 暂缓项永远没人重看 | 暂缓清单无复审机制 | 随版本评审重读，触发条件达成即立项 |
| 风险清单沦为走过场 | 只有描述没有检测信号 | 每条有信号/应对/owner/复审日 |
| 需求变了但文档没变 | 代码先行、文档后追 | 变更先改需求与验收标准 |

## 先设计测试矩阵，再开始实现

这里的「测试」测的是**立项包本身**，不是代码：

| 维度 | 要覆盖 |
|---|---|
| 完整性 | 主大纲一档每项有答案 + 验收证据；无「后续补充」充当已完成 |
| 范围 | in-scope 与 non-goals 逐条具体；成功标准可测 |
| 追踪 | 每条需求有四列链路；孤儿数为 0 或已登记债 |
| 决策 | 重大选择 ADR 齐全，每份有备选、理由、状态、触发条件 |
| 风险 | 每条有检测信号与复审日；无空白 owner |
| 暂缓 | 逐条理由 + 触发条件；与五档清单一致 |
| 变更 | 故意发起一次范围/接口变更，确认模板与门真的拦住 |
| 交接 | 换一个人只读立项包，能否复述「做什么、不做什么、凭什么算完成」 |

最后一条是验收的验收：**文档写给自己看得懂不算数，接手的人不追问也能开工才算数。**

## 给 AI 的实施约束模板

> 先产出立项包：一页范围说明（含明确 non-goals 与可测成功标准）、RACI、需求与 Given/When/Then 验收标准、需求↔设计↔实现↔测试追踪矩阵、重大选择的 ADR 目录（每份含备选、被否决理由、状态、触发重评条件）、决策日志、风险登记（检测信号/影响/应对/owner/复审日）、变更控制模板、暂缓清单与复审机制，然后逐档回答主大纲的准入问题。**没有答案的项标「未完成」，不得写「后续补充」充当已完成；暂缓必须带书面理由与触发重新评估的条件；non-goals 与暂缓项不得混写；聊天里的结论必须转成在库条目；需求变更先改验收标准再改实现。** 立项包与 ADR 使用当前项目的事实，示例值只能是占位符，不得从其他项目照抄产品名、ID、平台策略或合规范围。完成后用「接手人只读文档能否开工」自检，并列出未决问题与责任人。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 范围说明、non-goals、成功标准、RACI、一档问题的答案与证据——**本方案是五档的前置门槛** |
| 二档 | 追踪矩阵无孤儿、ADR 目录齐备、必需门与变更控制就位 |
| 三档 | 带债登记的 owner 与偿还节点、风险登记复审 |
| 四档 | 合规/安全/发布门的核销记录、未验项明确列出 |
| 五档 | 暂缓清单的建立与随版本重读机制；触发条件达成即转立项 |
