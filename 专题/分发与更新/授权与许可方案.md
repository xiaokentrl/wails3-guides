# 授权与许可方案：通用规划方案

## 这份方案是做什么的

来源：主大纲五档「授权与许可」暂缓项（原话：当前无商业授权机制；引入授权/订阅时，机器绑定、离线宽限、试用期与升级路径需整体立项，不得散落在启动流程里）、商业桌面软件许可实践（试用/永久/订阅、离线激活、时钟回拨检测、硬件指纹）、《供应链安全与依赖治理方案》的许可证矩阵（那是**第三方依赖的开源许可证义务**，与本文的**产品商业授权**是两件事，别混）。

母法方案：《登录与权限方案》（账号与会话）、《本地敏感数据与密钥管理方案》（许可证签名与密钥）、《应用状态与持久化技术方案》（许可状态落盘）、《单实例与快速启动方案》（启动期检查）、《版本号方案》与《签名打包与更新分发技术方案》（升级路径）、《操作反馈方案》（到期提示）。

它管**「谁可以在什么条件下用这个功能、离线时怎么判、换机/重装/降级怎么办」**。不预设：是否商业化、许可模型、试用天数、是否联网、是否绑定机器。所有具体值由产品与法务决定。

## 开始写代码前，先让 AI 回答这些问题

1. 许可模型是什么：无授权（当前）、试用、永久、订阅、按席位、按用量？各功能的门控粒度（整个应用 / 功能开关 / 用量上限）？
2. 试用期从何时起算、如何防重置（重装、清配置、改时钟、换账户）？到期后的行为是只读、禁用还是提醒？
3. 是否需要离线可用？完全气隙环境（无网络）如何激活与续期？离线宽限期多长、由谁批准延长？
4. 机器绑定用什么标识？硬件变更、虚拟机、系统重装、多设备时如何处理？是否允许用户在自助门户解绑？
5. 许可证文件/令牌的签名与验签在哪？公钥是否固定在二进制内（→《签名打包与更新分发技术方案》的信任根纪律）？
6. 客户端校验能被绕过吗？**关键校验是否在服务端强制**，本地判定只是体验优化（→《登录与权限方案》《威胁建模与安全响应方案》）？
7. 时钟回拨检测用什么（单调时钟、可信时间源、递增计数器）？误判时用户如何恢复？
8. 许可状态存在哪、是否加密/防篡改、损坏时是「拒绝启动」还是「降级为试用」（→《应用状态与持久化技术方案》）？
9. 升级/降级/换版本时许可状态如何迁移？旧版本能否识别新格式并明确拒绝？
10. 到期、过期、验证失败、网络不可达、服务器错误，分别给用户什么提示与恢复入口（→《操作反馈方案》）？
11. EULA/退款/订阅条款如何随安装与首次运行呈现？多语言与版本化（→《多语言实现方案》《用户文档与上手支持方案》）？
12. 许可验证失败是否会产生诊断记录？记录里是否含个人信息（→《日志与可诊断性技术方案》《遥测与隐私合规方案》）？
13. 若当前不引入授权（五档暂缓），触发重新评估的条件写在哪？

交付给 AI 的设计结果应包含：许可模型与门控矩阵、试用与离线策略、机器绑定与迁移、签名验签方案、时钟与状态落盘、服务端强制点、失败提示与恢复、EULA 与升级路径。

## 核心纪律

### 一、整体立项，不散落在启动流程

| 项 | 要写清 | 验收证据 |
|---|---|---|
| 门控矩阵 | 功能 × 许可档位 × 到期行为 | 单一注册表，UI 与领域层共用同一份判定 |
| 判定归属 | 领域层判定，UI 只呈现 | 权限判定位置清单（→《登录与权限方案》） |
| 启动期检查 | 是否阻塞主线程、是否在依赖就绪后（→《依赖顺序方案》《单实例与快速启动方案》） | 启动里程碑耗时实测 |
| 单一入口 | 许可校验集中在一处，禁止各页面各判一次 | 静态扫描判定点数量 |
| 暂缓记录 | 无授权机制时的理由与触发条件 | 立项包条目（→《立项范围与决策记录方案》） |

**最常见的坏味道是「启动脚本里加一句 if」**：试用、离线宽限、机器绑定、升级迁移会陆续被塞进启动流程，最后没人说得清判定顺序。

### 二、试用、离线与机器绑定

| 决策 | 要点 | 禁止 |
|---|---|---|
| 试用起算 | 首次启动写一次状态；防重置靠不可轻易清除的位置 + 服务端记录（若有账号） | 只靠一个本地文件，删掉就重置 |
| 离线宽限 | 明确天数、续期方式、宽限期内功能范围、延长审批 | 无限宽限、静默延长 |
| 气隙激活 | 离线挑战/响应或签名许可文件；验签公钥固定在二进制内 | 从更新源动态取公钥 |
| 机器绑定 | 稳定标识 + 变更容忍阈值 + 自助解绑路径 | 用易变字段（网卡 MAC 单值）硬绑定且无申诉 |
| 迁移 | 重装、换机、虚拟机、多设备各写一条路径 | 「重装后重新买一次」 |

### 三、时钟、状态与篡改

- 墙钟可被用户回拨；时长/宽限判断用单调时钟或可信时间源 + 单调递增计数（→《数据模型与数据契约方案》的时间口径纪律）。
- 时钟回拨误判必须有用户可恢复路径（联网校时、联系支持码），不能把付费用户锁死。
- 许可状态落盘沿用持久化纪律：预写备份、有效性门、损坏降级明确（→《应用状态与持久化技术方案》）；本地状态可加密/签名，但**不要写成「客户端不可篡改」**——用户控制设备，本地判定只是体验层（→《威胁建模与安全响应方案》）。
- 关键校验在服务端强制：订阅有效性、席位、用量配额不能被本地布尔值覆盖（→《登录与权限方案》）。
- 许可文件与日志不含个人信息；诊断记录只留关联 ID 与错误码（→《日志与可诊断性技术方案》《遥测与隐私合规方案》）。

### 四、失败与升级路径

| 场景 | 用户看到什么 | 恢复入口 |
|---|---|---|
| 试用到期 | 明确到期与可选动作 | 购买/激活/导出数据 |
| 网络不可达（宽限内） | 还剩几天、功能范围 | 稍后重试、离线激活 |
| 服务器错误 | 不是「许可无效」，区分服务端故障 | 重试 + 状态页 |
| 许可文件损坏 | 明确原因，不静默降级为试用 | 重新激活、导入许可 |
| 升级到新版本 | 许可状态迁移成功或明确失败 | 回滚到旧版本（→《签名打包与更新分发技术方案》） |

**导出数据永远可用**：无论许可状态如何，用户应能导出自己的数据（→《数据可携带与彻底删除方案》）。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 删配置就能重置试用 | 起算状态只在易删文件 | 多重状态 + 服务端记录 + 明确防重置目标（不承诺不可破） |
| 改系统时间延长许可 | 用墙钟算宽限 | 单调时钟/可信时间 + 递增计数 |
| 离线客户装完用不了 | 无气隙激活与离线宽限设计 | 离线挑战/响应 + 明确宽限策略 |
| 换机后许可丢失且无自助解绑 | 硬绑定且无迁移路径 | 变更容忍 + 自助解绑 + 审批例外 |
| 服务端故障被显示成「许可无效」 | 错误分类不清 | 错误分类表 + 独立恢复入口 |
| 本地改布尔值提权 | 把客户端判定当授权 | 服务端强制 + 领域层判定 |
| 升级后许可全丢 | 状态 schema 无迁移与降级保护 | 迁移函数 + 版本守卫（→《应用状态与持久化技术方案》） |
| 授权逻辑散在启动脚本各处 | 没有整体立项 | 门控矩阵 + 单一判定入口 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 门控 | 每个功能 × 每档许可 × 到期/过期/只读状态 |
| 时钟 | 回拨、跨时区、DST、长时间关机的宽限计算 |
| 状态 | 重装、清配置、损坏文件、升级/降级迁移、多设备 |
| 离线 | 首次离线、宽限内/外、气隙激活、服务器错误、恢复联网 |
| 安全 | 改本地状态、替换许可文件、篡改签名、过期公钥轮换 |
| 体验 | 到期提示、导出数据、自助解绑、支持码恢复 |
| 形态 | dev / 打包安装分别跑；未联网环境真实断网测试 |

## 给 AI 的实施约束模板

> 先给出许可模型与门控矩阵、试用与离线宽限策略、机器绑定与迁移路径、签名验签与公钥固定位置、时钟与状态落盘方案、服务端强制校验点、失败提示与恢复入口、EULA 呈现与升级迁移流程，再写启动检查代码。**授权逻辑整体立项，集中在领域层单一判定入口，UI 只呈现；本地判定只是体验层，关键校验在服务端强制；不得声称客户端不可篡改；时钟回拨用单调时钟或可信时间源并给用户恢复路径；离线/气隙激活与宽限期必须事先设计；许可状态迁移要有版本守卫与降级拒绝；无论许可状态如何都要能导出用户数据。** 当前若不引入授权，把理由与触发重新评估的条件写进立项包并随版本复审。实现后给出门控、时钟、篡改、离线、迁移的可观察测试，并明确哪些是「提高成本」而非「不可破解」。所有模型、天数、标识由当前项目与法务决定；任何「已激活」「已到期」「已迁移」必须附可观察证据（产物断言、演练记录、时钟回拨用例），不得只写状态变更。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 是否商业化的决策与暂缓记录（不回答不写启动检查） |
| 二档 | 门控矩阵、试用/离线策略、判定入口、服务端强制点 |
| 三档 | 失败提示、导出数据、EULA 呈现、多语言 |
| 四档 | 气隙激活演练、公钥轮换、升级迁移与回滚、法务文书 |
| 五档 | 按主大纲原暂缓项：当前无授权机制，保留理由与触发条件；引入时整体立项 |
