# 供应链安全与依赖治理方案：通用规划方案

## 这份方案是做什么的

来源：主大纲四档「SBOM 与依赖锁定」「依赖 CVE 扫描」「杀软/EDR 白名单」「UPX 误报」「符号剥离与堆栈还原」，以及 OWASP DA9（含已知漏洞组件）、桌面应用供应链实践（SBOM/SCA/构建环境完整性/签名密钥 HSM）、开源许可证合规清单（许可证分类、NOTICE、审批证据）。

母法方案：《签名打包与更新分发技术方案》（签名、公证、回滚）、《CI矩阵与质量门禁方案》（门禁与证据）、《产品身份单一源方案》（构建产物清单）、《Go测试与文件系统模式方案》（依赖注入与可复现）、《发布交付流水线方案》（交付链）。

它管**「这个二进制里到底有什么、是谁在什么时候装进来的」**：依赖引入规则、锁定与升级节奏、SBOM/CVE、许可证义务、构建环境完整性、发布前的第三方风险核对。不管版本号数值（→《版本号方案》）、不管签名算法（→《签名打包与更新分发技术方案》）、不管运行时凭据（→《本地敏感数据与密钥管理方案》）。

不预设：CI 平台、SBOM 格式、扫描工具、许可证策略、白名单厂商清单。所有具体值由项目与法务决定，未核实的标**待验证**。

**证据等级**：SBOM/CVE 工具与格式为行业通行做法；许可证义务与响应时限属法律/合规条款，由法务确认；框架与构建环境行为标 **待验证**。

## 开始写代码前，先让 AI 回答这些问题

1. 依赖引入规则：新增一个依赖需要谁批准？评估哪些维度（维护活跃度、许可证、原生依赖、是否引入 cgo）？
2. `go.mod` / 前端锁文件是否按哈希固定？`go mod verify`、`go mod tidy` 是否在 CI 中执行？
3. CI 是否生成 SPDX 或 CycloneDX 格式的 SBOM？何时生成、存档多久、如何按版本查回？
4. 是否配置 `govulncheck` 或等效扫描？CVE 的响应时限、豁免流程与 owner 是谁？
5. 许可证策略：哪些类别预批准、哪些需评审、哪些禁止（GPL/AGPL/未知/自定义/非商业）？谁负责解释与例外批准？
6. NOTICE / 许可证文本如何随分发物提供？源码 bundles、修改过的依赖、静态链接各有什么义务？
7. 构建环境是否可复现：固定 runner 镜像、固定工具链版本、不可变构建代理、外部制品签名/校验和验证？
8. 签名私钥存在哪（HSM / 托管密钥）？谁有权使用、轮换与吊销流程是什么（→《签名打包与更新分发技术方案》）？
9. 若启用 UPX/压缩，是否在目标安全软件下验证不误报、且完整跑过启动冒烟？混淆是否影响绑定 ID 稳定性？
10. 企业分发场景：是否按证书或哈希向主要安全厂商提交白名单？提前量多少？签名不等于不被拦截，验证记录在哪？
11. 符号剥离后，崩溃诊断是否依赖独立符号文件还原可读堆栈？符号文件如何归档与保密（→《崩溃上报与符号还原方案》）？
12. 子处理者/供应商清单：云、CDN、崩溃监控、更新服务、支持工具分别在哪个环节接触数据（→《遥测与隐私合规方案》）？
13. 门禁与证据：哪些门红了阻断发布？结果如何与版本、提交哈希绑定，供事后审计（→《CI矩阵与质量门禁方案》）？

交付给 AI 的设计结果应包含：依赖引入策略、锁定与升级节奏、SBOM/CVE 流程、许可证矩阵与 NOTICE、构建可复现说明、白名单/UPX/符号决策、供应商清单、门禁证据表。

## 核心纪律

### 一、依赖引入：先分类，再批准

| 类别 | 例子 | 处理 |
|---|---|---|
| 预批准 | 许可证宽松、维护活跃、纯 Go/纯 TS | 直接引入，进锁文件 |
| 需评审 | LGPL/MPL/EPL、含 cgo、含平台原生库、修改过的依赖 | 记录用途、链接方式、替代方案与批准人 |
| 禁止 | 未知/自定义/非商业/领域限制许可、明确高危组件 | 不引入；确需则走例外审批并由法务签字 |

每条依赖登记：用途、许可证、版本、哈希、引入版本、owner、下次复审日。**「先装上看能不能跑」不是引入流程**；评审结论要在库内可查，不留在聊天记录（→《立项范围与决策记录方案》的决策日志纪律）。

### 二、锁定、SBOM 与 CVE

- 锁文件按哈希固定；CI 跑 `go mod verify` / `go mod tidy` 一致性检查，有差异即失败。
- 每次发布产物生成 SBOM（SPDX 或 CycloneDX），按版本号归档；零日爆发时能立刻查「哪个版本含这个库」。
- 扫描工具（govulncheck / SCA）在 PR 与发布前各跑一次；阻断规则写明严重度阈值与豁免流程（谁批、有效期、复审日）。
- CVE 响应时限是**产品承诺**，不是「尽快」：写明分级时限、通知对象与验证方式。
- 构建环境完整性：固定工具链、不可变 runner、外部制品校验签名与哈希；禁止构建脚本从公网临时拉取未固定版本（→《CI矩阵与质量门禁方案》）。

### 三、许可证义务与 NOTICE

| 义务 | 落地形态 | 验收证据 |
|---|---|---|
| 许可证文本 | NOTICE / THIRD-PARTY 文件随分发物 | 产物内文件清单比对 SBOM |
| 源码提供 | 按许可证要求提供对应源码或获取方式 | 法务确认记录 |
| 修改声明 | 修改过的依赖单独标注 | 依赖登记表「是否修改」列 |
| 例外批准 | 需评审类别的书面批准 | 审批单 + 关联 SBOM 条目 |

**SBOM 是工程产物，DPA/NOTICE 是法律产物**，两者要能互相指认；法务与工程各自 owner 明确。每次新增 SDK、改日志留存、改遥测字段都可能改变供应商角色，文书要跟着更新（→《遥测与隐私合规方案》）。

### 四、发布前的第三方风险核对

| 项 | 决策 | 必须验证 |
|---|---|---|
| 杀软/EDR 白名单 | 是否提交、按证书还是哈希、提前量 | 目标安全软件实测；签名 ≠ 不被拦截 |
| UPX / 压缩 | 是否启用 | 误报实测 + 完整启动冒烟；与前端构建目标的兼容性 |
| 混淆 | 是否启用 | 绑定 ID 稳定性、调试能力下降是否被接受 |
| 符号剥离 | 是否剥离 | 独立符号文件归档与堆栈还原演练 |
| 差分/回滚包 | 是否保留旧版 | 回滚触发条件与验证流程（→《签名打包与更新分发技术方案》） |
| 供应商清单 | 谁接触数据、存哪、如何删除 | 子处理者清单 + 删除路径 |

任何一项「先跳过、发布后补」都要登记为带触发条件的债，不能静默消失。

### 五、证据绑定

每次发布保留：提交哈希、SBOM、扫描结果、许可证审批、构建环境版本、签名/公证记录、符号文件索引、白名单提交记录。发布时按版本号能查回这一组证据；清理 CI 运行记录时**不要连门禁证据一起删**（→《CI矩阵与质量门禁方案》的保留策略）。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 零日爆发时查不出哪些版本受影响 | 无 SBOM 或未按版本归档 | 每版生成 + 按版本可检索 |
| CI 绿但产物含未锁定依赖 | 锁文件/工具链未固定，构建脚本临时拉包 | 哈希固定 + 不可变 runner + tidy/verify 门 |
| 法务审查发现 GPL 依赖 | 引入时无许可证分类与批准 | 三类矩阵 + 审批证据 |
| NOTICE 漏条目 | 手写 NOTICE，未与 SBOM 对账 | 产物内清单比对 SBOM |
| 签名包仍被杀软拦截 | 以为签名等于白名单 | 目标安全软件实测 + 提前提交 |
| UPX 后启动崩溃/前端目标不兼容 | 只测了体积没跑冒烟 | 误报 + 完整启动冒烟 |
| 剥离符号后堆栈不可读 | 无独立符号文件与还原演练 | 符号归档 + 还原演练 |
| 发布后查不到当时扫描结果 | 证据未与版本绑定、运行记录被清理 | 证据按版本存档 + 清理保留策略 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 锁定 | 故意改锁文件/删哈希，门必须红 |
| SBOM | 产物内依赖与 SBOM 逐条对账；按版本可检索 |
| 扫描 | 故意引入一个已知漏洞版本，确认阻断与豁免流程 |
| 许可证 | 需评审/禁止类别各造一个用例，确认无法静默合入 |
| 构建 | 干净 runner 从零构建，产物哈希与既定值一致 |
| 分发 | 未签名/签名/UPX/剥离符号四种产物分别跑安装与启动冒烟 |
| 回滚 | 差分更新失败后回退到旧版本的演练（→《签名打包与更新分发技术方案》） |
| 证据 | 按版本号查回整组证据；故意清理运行记录后证据仍在 |

## 给 AI 的实施约束模板

> 先给出依赖引入策略与三类许可证矩阵、锁定与升级节奏、SBOM/CVE 流程与响应时限、NOTICE 生成方式、构建可复现说明、白名单/UPX/混淆/符号剥离决策、供应商清单与门禁证据表，再写构建脚本。**锁文件按哈希固定并在 CI 验证；每版生成 SBOM 并按版本归档；扫描有阻断阈值与豁免流程；NOTICE 必须与 SBOM 对账；构建环境不可变、外部制品校验签名与哈希；签名不等于不被杀软拦截，必须实测；符号剥离要有独立符号文件与还原演练。** 任何「先跳过发布后补」登记为带触发条件的债。实现后给出故意失败用例（改锁文件、引入漏洞版本、漏 NOTICE 条目）证明门真的红，并列出未实测的安全软件与平台。所有工具、格式、阈值、时限由当前项目与法务决定，查不到依据的写「待验证」。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 依赖引入规则、许可证三类矩阵、锁定原则 |
| 二档 | CI 的 verify/tidy/扫描门、NOTICE 生成、构建环境可复现 |
| 三档 | 供应商清单、豁免流程、符号文件归档 |
| 四档 | SBOM 与 CVE 扫描、杀软白名单、UPX/混淆评估、证据按版本绑定——**缺项不得发布** |
| 五档 | 差分更新、HSM 级密钥托管可按产品风险暂缓（写理由 + 触发条件） |
