# 用户文档与上手支持方案：通用规划方案

## 这份方案是做什么的

来源：行业 kickoff / 产品支持清单「交付文档、上手引导、支持交接与维护 owner」、生产就绪评审的「交接给支持与长期维护责任人」、GDPR 清单「隐私政策在应用内首次运行展示并随时可查」、主大纲三档「诊断支持包」与《发布交付流水线方案》的发布说明纪律。

母法方案：《操作反馈方案》（反馈层级与时效）、《弹窗按钮文案方案》（按钮写结果）、《国际化与输入技术方案》《多语言实现方案》（键化与翻译）、《日志与可诊断性技术方案》（诊断包内容）、《遥测与隐私合规方案》（隐私政策与同意）、《系统能力与平台集成技术方案》（权限申请时机）、《测试策略与验收总纲》（UAT 与交接）。

它管**用户拿到应用之后靠什么学会用、卡住时怎么求助、支持团队靠什么排障**：首次运行引导、帮助文档体系、应用内反馈通道、诊断包的用户侧说明、支持 runbook 与维护交接。不预设：文档平台、语言数量、支持渠道、是否配客服系统。

## 开始写代码前，先让 AI 回答这些问题

1. 首次运行要用户做哪些决定（权限、目录、语言、许可、同意）？**每项申请的时机与理由**是什么（→《系统能力与平台集成技术方案》《遥测与隐私合规方案》）？
2. 引导能否跳过、能否重看？跳过后的功能是否仍可发现？
3. 帮助文档的版本化策略是什么（随版本归档 / 在线最新 / 应用内嵌）？离线可用吗？
4. 文档是否随产品一起键化与翻译？新增语言时文档如何同步（→《多语言实现方案》）？
5. 隐私政策、EULA、第三方许可证文本在哪里呈现：首次运行、设置内常驻、安装包内（→《授权与许可方案》《供应链安全与依赖治理方案》）？
6. 应用内反馈/问题上报通道是什么？用户附上诊断包时**默认包含什么、排除什么、是否需要二次确认**（→《日志与可诊断性技术方案》《遥测与隐私合规方案》）？
7. 常见错误是否有可操作的自助恢复步骤，而不是只显示错误码（→《状态码方案》《操作反馈方案》）？
8. 支持 runbook 有没有：每个高频告警/工单类别的排查步骤、升级路径、需要的日志、用户可执行的收集动作？
9. 支持团队是否参与过一次真实调试的影子演练？上线前 top 3 工单类别的应对是否已准备？
10. 长期维护 owner 是谁？文档、runbook、诊断包说明各由谁更新，随版本评审的机制是什么？
11. 发布说明是否从结构化条目生成、用户能否看懂「对我有什么影响」（→《发布交付流水线方案》）？
12. 文档与 UI 文案是否同源？升级/改名后文档里的旧名称如何清理（→《产品身份单一源方案》）？
13. 无障碍：文档与引导是否可被读屏/键盘访问（→《无障碍与辅助技术方案》）？

交付给 AI 的设计结果应包含：首次运行引导流程、文档体系与版本化、政策文本呈现、反馈通道与诊断包边界、支持 runbook、维护交接、发布说明与用户验收。

## 核心纪律

### 一、首次运行：权限申请要讲理由，且可跳过

| 项 | 要求 | 禁止 |
|---|---|---|
| 时机 | 在功能真正需要时才申请，不首屏一次性要全套权限 | 一进应用就弹三四个系统授权框 |
| 理由 | 每个权限写清「用来做什么、不给会怎样」 | 「为了提供更好的体验」 |
| 可跳过 | 引导可跳过、可重看；跳过后入口仍可发现 | 跳过即永久失去功能入口 |
| 拒绝后 | 明确降级路径与恢复入口（→《系统能力与平台集成技术方案》） | 静默禁用、反复弹窗 |
| 同意 | 必需与可选分层，撤回入口常驻（→《遥测与隐私合规方案》） | 一个「接受」全包 |
| 首次运行验证 | 用全新用户账户、无配置无文件的环境跑一遍 | 只在开发者自己的机器上验 |

### 二、文档体系：版本化、可离线、随产品翻译

- 文档与产品版本对应：随版本归档或应用内嵌；用户装的是旧版时不能只看到最新版的说明。
- 离线场景（内网/气隙/飞行模式）下核心帮助仍可访问；在线文档要有降级。
- 文案与 UI 同源键化，语言切换时文档与界面一起更新（→《国际化与输入技术方案》《多语言实现方案》）。
- 政策类文本（隐私政策、EULA、第三方许可证）在应用内首次运行展示且随时可查；变更要留版本与生效日期。
- 文档里的产品名、路径、菜单项从身份/目录单源派生或校验，避免改名后文档全是旧称（→《产品身份单一源方案》《默认安装目录规划方案》）。

### 三、反馈通道与诊断包边界

| 项 | 规则 |
|---|---|
| 默认内容 | 应用版本、平台/会话类型、错误码、关联 ID、脱敏后的配置摘要 |
| 默认排除 | token、文件内容、用户文档、完整路径中的用户名、截图/自由文本（需显式附加） |
| 用户确认 | 附加可选内容前二次确认，说明会发送什么、到哪、留多久（→《弹窗按钮文案方案》） |
| 撤回 | 同意撤回后不再上传；已上传的删除路径可执行（→《遥测与隐私合规方案》） |
| 自助 | 常见错误给出可操作步骤，而非只显示码值（→《状态码方案》） |

**诊断包是「用户主动给出的东西」**，不是应用悄悄收集的东西；内容清单要写在设置里可读（→《日志与可诊断性技术方案》）。

### 四、支持交接与维护 owner

- 每个高频告警/工单类别一份 runbook：含义、初步排查、需要哪些日志、缓解动作、升级路径（→《威胁建模与安全响应方案》的事件 runbook 同理）。
- 上线前：支持工程师影子参与一次真实调试，runbook 走查，top 3 工单类别的应对准备好。
- 明确长期维护 owner：**「大家一起维护」等于没人维护**；文档、runbook、诊断包说明各有 owner 与复审节点。
- 发布说明由结构化条目生成，写「对用户的影响」与「需要用户做什么」（→《发布交付流水线方案》）。
- UAT 由真实用户在目标安装形态执行并记录环境与结论（→《测试策略与验收总纲》）。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 首屏连弹授权框，用户直接退出 | 权限申请时机与理由未设计 | 按需申请 + 理由 + 可跳过 |
| 用户找不到「跳过之后去哪开」 | 引导跳过即失去入口 | 入口常驻设置/帮助 |
| 旧版用户看到新版文档 | 文档只维护在线最新版 | 版本化归档或应用内嵌 |
| 诊断包带出用户文件内容 | 默认全量收集、无二次确认 | 白名单 + 显式附加 + 上传前确认 |
| 支持团队答不上来 | 无 runbook、无影子演练、无 owner | runbook + 上线前演练 + 维护责任人 |
| 改名后文档全是旧称 | 文档与产品身份不同源 | 单源派生或校验 |
| 错误提示只有码值 | 文案与错误码未解耦 | 码定事实、文案给可操作步骤 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 首启 | 全新账户、无配置/无文件、拒绝每项权限、跳过引导后重看 |
| 文档 | 版本对应、离线可用、语言切换、政策文本可随时查看 |
| 诊断包 | 默认内容白名单、故意塞入敏感文件断言不上传、二次确认流程 |
| 自助 | 高频错误的可操作步骤可走通 |
| 支持 | 按 runbook 处理一次模拟工单并计时；top 3 类别走查 |
| 交接 | 换一个人只读文档与 runbook 能否接手 |
| 无障碍 | 引导与帮助的键盘/读屏可达（→《无障碍与辅助技术方案》） |

## 给 AI 的实施约束模板

> 先给出首次运行引导流程（每项权限的时机/理由/拒绝降级）、文档版本化与离线策略、政策文本呈现位置、反馈通道与诊断包内容白名单、支持 runbook、维护 owner 与发布说明规则，再写引导代码。**权限按需申请且写清理由，引导可跳过可重看，跳过后入口常驻；文档随版本归档并离线可用、随 UI 一起键化翻译；隐私政策/EULA/许可证文本应用内首次运行展示且随时可查；诊断包默认排除用户内容与凭据，附加可选内容需二次确认；每个高频工单一 runbook 并做影子演练；文档、runbook、诊断包说明各有明确维护 owner。** 任何「大家一起维护」「为了更好体验」这类无判据表述退回重写。实现后用全新用户账户跑一遍首启与 UAT，并列出未覆盖语言与平台。所有渠道、文本、owner 由当前项目需求决定。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 首次运行权限时机与文档版本化决策（不回答不写引导代码） |
| 二档 | 引导流程、政策文本呈现、诊断包边界、错误自助步骤 |
| 三档 | 文档翻译与离线、反馈通道、runbook 初版 |
| 四档 | 支持影子演练、维护 owner 交接、UAT 记录、发布说明用户视角——缺项不得发布 |
| 五档 | 多语言完整文档、在线帮助中心可按目标市场暂缓（写理由 + 触发条件） |
