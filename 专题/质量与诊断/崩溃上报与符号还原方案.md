# 崩溃上报与符号还原方案：通用规划方案

## 这份方案是做什么的

来源：主大纲四档「符号剥离与堆栈还原」、三档「诊断支持包」、隐私友好的崩溃上报实践（opt-in、字段白名单、上传前脱敏、自编译构建零上报），以及《供应链安全与依赖治理方案》里符号文件归档的那一半。

母法方案：《日志与可诊断性技术方案》（panic 落盘、异常退出检测、诊断包）、《遥测与隐私合规方案》（同意、留存、删除、子处理者）、《本地敏感数据与密钥管理方案》（脱敏与传输）、《性能与资源基线技术方案》（NFR）、《测试策略与验收总纲》（回归）、《签名打包与更新分发技术方案》（产物与版本）。

它管**「应用崩了之后，团队怎样在不窥探用户的前提下拿到可读的堆栈」**：本地崩溃落盘、同意与字段白名单、符号文件与还原、版本/渠道关联、保留期与删除。不管业务日志内容契约（→《日志与可诊断性技术方案》）、不管遥测全量合规（→《遥测与隐私合规方案》）。

不预设：是否启用远程上报、上报服务、符号格式、保留期。未核实的行为标**待验证**。

## 开始写代码前，先让 AI 回答这些问题

1. 崩溃是否只本地落盘，还是远程上报？远程上报是否需要 opt-in？默认状态是什么（→《遥测与隐私合规方案》）？
2. 本地崩溃文件包含什么（panic 详情、堆栈、版本、平台、会话类型）？**排除什么**（文件内容、路径中的用户名、token、自由文本）？
3. 下次启动是否检测异常退出并提示用户？提示是否给「查看/发送/删除」三个明确动作（→《日志与可诊断性技术方案》《弹窗按钮文案方案》）？
4. 上报字段白名单由谁维护？新增字段是否触发隐私复审与文书更新？
5. 上传前脱敏在哪个执行点？脱敏失败是丢弃还是标记待审（→《本地敏感数据与密钥管理方案》）？
6. 剥离符号后，可读堆栈依赖哪份符号文件？符号文件如何按版本/构建哈希归档、谁有权访问、保留多久（→《供应链安全与依赖治理方案》）？
7. 还原流程：从收到的堆栈到可读函数名，需要哪些输入（版本、构建 ID、平台、架构、符号索引）？是否演练过？
8. 版本/渠道/构建哈希如何与崩溃记录关联，避免「这份堆栈属于哪个构建」要靠猜（→《版本号方案》《产品身份单一源方案》）？
9. 自编译构建、无账号构建是否默认零上报？构建门如何证明（→《生产构建安全基线方案》）？
10. 上报失败、离线、服务不可用时的行为：排队重放？上限？是否影响核心功能（→《网络与离线弹性技术方案》）？
11. 保留期与删除：崩溃记录、堆栈、支持附件、聚合指标各自多久？用户撤回同意后已上传数据怎么删（→《遥测与隐私合规方案》）？
12. 崩溃率/启动失败率是否纳入 NFR 与发布门禁？阈值与测量方法是什么（→《性能与资源基线技术方案》）？
13. 崩溃恢复与渲染进程失败是否区分处理（→《WebView2运行时与图形可靠性方案》《窗口与多窗口技术方案》）？

交付给 AI 的设计结果应包含：崩溃数据清单、同意与白名单、本地落盘与下次启动检测、符号归档与还原流程、版本关联、失败策略、留存删除、NFR 与门禁。

## 核心纪律

### 一、字段白名单，而不是「堆栈里有什么就发什么」

| 允许（示例） | 排除（示例） |
|---|---|
| 错误码、脱敏后的堆栈、应用版本、构建哈希、平台/架构/会话类型、关联 ID | token、邮箱、自由文本输入、用户文档内容、完整本地路径、设备名、环境变量、截图、密钥 |

- 白名单是**代码级常量**，新增字段走评审；黑名单永远漏掉下一次新增的敏感字段。
- 脱敏在**写入/上传前**完成；后处理只是第二道防线（→《本地敏感数据与密钥管理方案》）。
- 同意分层：必要更新交付 ≠ 可选诊断上报；拒绝后核心功能与更新仍可用，撤回入口常驻（→《遥测与隐私合规方案》）。
- 自编译构建默认零上报，且由构建 tag 与产物探测门证明（→《生产构建安全基线方案》）。

### 二、本地落盘与下次启动

```
崩溃 → 本地落盘（白名单字段，不含用户内容）
  → 下次启动检测异常退出
    → 用户可见提示：查看 / 发送（需同意）/ 删除
      → 发送失败：排队重放有上限，不影响核心功能
```

- panic handler 位置、诊断文件路径、落盘失败的可诊断记录按《日志与可诊断性技术方案》的纪律；`InvokeSync*` 一类调用点的「不 panic」约束同样适用。
- 提示文案写结果、给三个明确动作，不含技术黑话（→《操作反馈方案》《弹窗按钮文案方案》）。
- 本地诊断文件也有留存上限与清理任务；用户导出诊断包时同样走白名单（→《用户文档与上手支持方案》）。

### 三、符号文件与还原

| 项 | 要求 |
|---|---|
| 生成 | 剥离符号前导出独立符号文件，按版本 + 构建哈希 + 平台/架构归档 |
| 保密 | 符号文件权限收紧、访问有记录；不随分发包下发 |
| 索引 | 崩溃记录携带构建哈希，能直接定位对应符号文件 |
| 还原 | 从收到的堆栈到可读函数名的步骤写成 runbook，并**真实演练一次** |
| 保留 | 符号文件保留期与崩溃记录一致或更长，写明理由；到期自动清理 |
| 缺失 | 符号文件缺失时明确标记「不可还原」，不假装读得懂 |

**「剥离了符号，崩溃堆栈就不可读」是常见发布事故**：四档要求「独立符号文件还原可读堆栈」，本方案把它落成可执行流程。混淆/UPX 对符号与绑定 ID 的影响见《供应链安全与依赖治理方案》《绑定层契约与生成物方案》。

### 四、失败、留存与门禁

- 上报失败/离线：排队重放带上界与过期，不无限堆积；服务不可用不影响核心功能（→《网络与离线弹性技术方案》《防抖与节流方案》）。
- 按存储位置定留存：本地诊断文件、服务端崩溃记录、支持附件、聚合指标各有到期任务；撤回同意后按删除流程处理已上传数据（→《遥测与隐私合规方案》）。
- 崩溃率/启动失败率纳入 NFR 与发布门禁：阈值、测量方法、采样口径成文；自动化回归未建立时写「手动测量」（→《性能与资源基线技术方案》《测试策略与验收总纲》）。
- 渲染进程失败与进程 panic 分开处理，恢复流程见《WebView2运行时与图形可靠性方案》。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 堆栈里带用户文件名/token | 黑名单脱敏、上传后处理 | 字段白名单 + 写入前过滤 |
| 剥离符号后堆栈不可读 | 无独立符号文件或无索引 | 按构建哈希归档 + 还原演练 |
| 不知道崩溃属于哪个版本 | 记录缺版本/构建哈希 | 版本单源注入崩溃头（→《版本号方案》） |
| 拒绝同意后仍在上报 | 同意只存在 UI，未进执行点 | 执行点统一校验 + 产物探测 |
| 离线后上报队列撑爆磁盘 | 无上界与过期 | 队列有界 + 过期清理（→《任务队列方案》） |
| 崩溃率涨了没人发现 | 无 NFR 阈值与告警 | 指标进发布门禁 |
| 自编译版本也在发数据 | 上报开关与构建形态无关 | 构建 tag + 产物能力探测 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 字段 | 故意塞入 token/路径/自由文本，本地文件与上传体均无命中 |
| 同意 | 首次询问、拒绝、撤回、自编译构建零上报 |
| 落盘 | 写入失败、磁盘满、下次启动检测、查看/发送/删除三动作 |
| 还原 | 用真实崩溃 + 归档符号跑通还原；符号缺失时明确标记 |
| 网络 | 离线排队、重放上限、服务 5xx、超时 |
| 留存 | 到期任务真实执行、撤回后删除链路 |
| 门禁 | 故意注入一次崩溃，确认告警/NFR 门可观察 |

## 给 AI 的实施约束模板

> 先给出崩溃数据白名单、同意与撤回流程、本地落盘与下次启动检测、符号文件归档与还原 runbook、版本/构建哈希关联、失败与留存策略、崩溃率门禁，再写上报代码。**默认只本地落盘；远程上报需 opt-in；字段白名单是代码级常量且脱敏在写入/上传前完成；拒绝同意或自编译构建零上报并由构建门证明；剥离符号前导出独立符号文件、按构建哈希归档并演练还原；上报队列有上界与过期且不影响核心功能；按存储位置设留存到期任务；崩溃率纳入 NFR 与发布门禁。** 任何「已脱敏」「已还原」必须附可观察证据（扫描无命中、还原出函数名）。实现后给出字段、同意、还原、留存、门禁的可观察测试，并列出未实测平台。所有字段、期限、阈值、服务由当前项目与法务决定。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 是否远程上报的决策、白名单与同意原则 |
| 二档 | 本地 panic 落盘、异常退出检测、版本关联 |
| 三档 | 上报队列、失败策略、用户可见的查看/发送/删除 |
| 四档 | 符号归档与还原演练、留存删除自动化、崩溃率门禁——缺项不得发布 |
| 五档 | 远程上报服务可按产品阶段暂缓（写理由 + 触发条件）；本地崩溃落盘不暂缓 |
