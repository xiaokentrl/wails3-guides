# 测试策略与验收总纲：通用规划方案

## 这份方案是做什么的

来源：主大纲五档「测试与验收总纲」暂缓项（原话：测试矩阵分散在各专题指南，CI 门禁见二档；多人协作、E2E 成为主力门禁时，再立跨指南的测试组织总纲）、行业 kickoff 清单「定义测试金字塔与覆盖率目标」「UAT/验收标准」，以及《CI矩阵与质量门禁方案》（门禁与矩阵）、《Go测试与文件系统模式方案》（Go 单测模式族）已覆盖但分散的部分。

本方案是**跨指南的组织总纲**：把散落在各专题里的测试要求收进一张分层表，定义每层测什么、谁维护、什么叫「做完」（DoD）、什么可以带债、债怎么登记。它不重写各专题的测试矩阵，也不重复 CI 命令清单（→《CI矩阵与质量门禁方案》）。

不预设：覆盖率数值、测试框架、团队规模、E2E 工具。所有具体值由项目决定。

## 开始写代码前，先让 AI 回答这些问题

1. 测试分几层？每层抓什么缺陷、由谁写、由谁维护、运行时机与失败语义（→《CI矩阵与质量门禁方案》）？
2. 各层覆盖率/数量目标是什么？**为什么是这个数**（不要抄別的项目）？覆盖率低时补测试还是改判定？
3. 单元层是否遵守表驱动、手写 fake、golden files 显式审查（→《Go测试与文件系统模式方案》）？前端是否同构（`it.each` / 快照 / 断言包装 / 轻 stub）？
4. E2E 覆盖哪几条主旅程？为何是这几条？其余功能靠哪层兜底？
5. 「依赖桌面的行为」如何在 CI 与手工之间分工：托盘手势、混合 DPI、通知权限、打包安装形态（→《托盘技术方案》《WebView2运行时与图形可靠性方案》）？
6. 验收标准（Given/When/Then）由谁写、什么时候写（→《立项范围与决策记录方案》）？DoD 包含哪些门（生成物、parity、类型、测试、产物、文档）？
7. 带债进 MVP 的登记格式是什么（owner、偿还节点、触发条件）？谁在版本评审重读？
8. flaky 用例的隔离、重试上限、复审日规则在哪（→《CI矩阵与质量门禁方案》）？
9. 性能与资源断言如何避免「本机恰好不超」（→《性能与资源基线技术方案》）？自动化回归何时建立（五档暂缓项）？
10. 视觉/快照回归如何避免 `-u` 一把梭？变更审查由谁签字？
11. 用户验收（UAT）由谁执行、在哪种安装形态、记录什么？
12. 每个专题的「测试矩阵」条目如何汇总到本总纲而不产生两份互相矛盾的清单？
13. 门禁自身是否被测试（故意失败验证门会红）？

交付给 AI 的设计结果应包含：层间组织规则（不复制用例矩阵）、覆盖率与 E2E 主旅程清单、DoD 清单、带债登记格式、flaky 与快照规则、UAT 计划、专题矩阵索引。

## 核心纪律

### 一、层间组织规则（不复制用例矩阵）

本表只定义各层职责边界；分层实现、命令与门禁统一以《CI矩阵与质量门禁方案》为准，本总纲不复制任何专题的用例矩阵。

| 层 | 抓什么 | 不抓什么 | Owner | 失败语义 |
|---|---|---|---|---|
| 单元 | 领域逻辑、纯决策、边界值、错误映射 | 启动、平台、UI 观感 | 写代码的模块 owner | 阻断 |
| 契约/生成器 | 生成物同步、错误码 parity、配置 Schema、语言键齐性 | 业务规则 | 基础设施 owner | 阻断 |
| 集成 | 落盘/网络/绑定/同步层组合 | 完整用户旅程 | 领域 owner | 阻断 |
| E2E（少量） | 安装→首启→主操作→退出/升级 | 细粒度分支 | E2E owner | 发布前阻断 |
| 手工/实机 | 托盘手势、混合 DPI、通知授权、离线、打包形态 | 可自动化的一切 | 测试 owner | 发布前核销 |

**E2E-heavy 金字塔是反模式**：慢、脆、失败原因难归属，最后被集体忽略。少数主旅程 + 强单元/契约层才稳。

### 二、DoD：什么叫「做完」

一条功能/修复在合并前至少核销：

1. 需求验收标准（Given/When/Then）可测且已跑（→《立项范围与决策记录方案》）；
2. 单元/契约层用例通过，新分支有断言（不是只测「函数被调用了」）；
3. 生成物、错误码 parity、类型检查、库内自查全绿（→《CI矩阵与质量门禁方案》）；
4. 可观察行为有回归测试：重复操作不重复生效、坏值不覆盖好值、同一入口注册数为 1（→《托盘技术方案》《应用状态与持久化技术方案》）；
5. 未实测平台/形态明确列出，发布说明不写完成式结论；
6. 文档、追踪矩阵、暂缓清单同步（→《立项范围与决策记录方案》）。

**「代码改对了」不等于「用户看到的行为变了」**：行为层证据优先于源码层（→《托盘技术方案》五层验证）。

### 三、带债、flaky 与快照

| 项 | 规则 |
|---|---|
| 带债进 MVP | 每条登记：缺口、影响、owner、偿还节点、触发条件；随版本评审重读 |
| flaky | 重试有上限、首次失败必留日志、连续失败自动隔离、隔离有 owner 与复审日；「just rerun」不是结论 |
| 快照/golden | 变更必须显式审查并说明为什么变；禁止批量 `-u` 一把梭（→《Go测试与文件系统模式方案》） |
| 性能断言 | 相对阈值 + 实测记录 + 测量方法；自动化回归未建立时写「手动测量」（→《性能与资源基线技术方案》） |
| 未验项 | 明确列出，不拿一个平台结果替其他平台背书 |

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 测试很多但线上仍出事 | 层间错位：拿 E2E 覆盖细分支、单元层没测纯决策 | 分层表 + 各层目标 |
| 覆盖率数字好看但没人信 | 只测「函数被调用」、快照批量更新 | 断言可观察行为 + 快照显式审查 |
| 发布说明写「已修复」仍复现 | 缺行为层证据与回归测试 | DoD 第 4/5 条 |
| flaky 越积越多 | 无条件重跑、无 owner | 重试上限 + 隔离 + 复审日 |
| 两份测试清单互相矛盾 | 总纲与 CI 篇各自定义一套分层规则 | 分层实现统一以《CI矩阵与质量门禁方案》为准，本总纲只定组织规则 |
| 带债永久不还 | 无偿还节点与版本评审 | 债登记 + 触发条件 |
| 本机性能过、CI 性能挂 | 绝对阈值来自某一台机器 | 相对阈值 + 测量方法记录 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 分层 | 每层至少一条「故意失败」用例，证明该层能抓到目标缺陷 |
| DoD | 造一个「编译通过但行为没变」的修复，确认 DoD 拦住 |
| 门禁自身 | 改生成物/删码映射/制造 flaky，确认门真的红并按规则隔离 |
| 形态 | dev / server / 打包安装；实机维度列手工清单 |
| UAT | 真实用户在目标安装形态下跑主旅程，记录环境与结论 |
| 索引 | 抽查若干专题矩阵链接，确认与本总纲不矛盾 |

## 给 AI 的实施约束模板

> 先给出层间组织规则（各层职责/owner/失败语义，不复制用例矩阵）、覆盖率与 E2E 主旅程清单、DoD 清单、带债登记格式、flaky 与快照规则、UAT 计划、专题矩阵索引，再写测试代码。**E2E 只覆盖少数主旅程；断言针对可观察行为而非「辅助函数被调用」；快照变更必须显式审查、禁止批量更新；flaky 重试有上限且首次失败留日志；未实测平台明确列出；本总纲只做索引不复制专题矩阵。** 每条功能按 DoD 逐项核销，缺项标为带债并写 owner 与触发条件。实现后给出故意失败用例证明每层与门禁真的会红，并列出未覆盖形态。所有覆盖率数值、框架、旅程清单由当前项目需求决定。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 沿用各专题既有测试矩阵；是否另立跨指南总纲的决策与暂缓记录（总纲本身按触发条件启用） |
| 二档 | 分层表、契约门、E2E 主旅程、带债登记——第一个可分发里程碑前锁定 |
| 三档 | flaky/快照规则、UAT、专题矩阵索引建立 |
| 四档 | 发布前 DoD 全量核销、未验项列出、门禁证据归档 |
| 五档 | 按主大纲原暂缓项：性能自动化回归、多人协作下的跨指南总纲可暂缓，须写理由与触发条件（E2E 成为主力门禁 / 多人协作时重评） |
