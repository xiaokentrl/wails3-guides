# 服务依赖与运维就绪方案：通用规划方案

## 这份方案是做什么的

来源：生产就绪评审（依赖所有权、服务期望、配额、超时、重试上限、回退行为、升级联系人、运营责任人与已接受风险）、行业 kickoff 清单「定义 SLO 与 error budget、告警只针对用户可感知症状、on-call runbook、上线 go/no-go 评审、交接给支持与维护 owner」。母法方案：《网络与离线弹性技术方案》（超时重试与离线）、《客户端与服务端API契约方案》（契约与限流）、《CI矩阵与质量门禁方案》（门禁证据）、《日志与可诊断性技术方案》（日志与关联 ID）、《性能与资源基线技术方案》（NFR）、《威胁建模与安全响应方案》（事件 runbook）、《用户文档与上手支持方案》（支持交接）、《崩溃上报与符号还原方案》（崩溃率）。

它管**「应用依赖的外部服务与后端，谁负责、出问题怎么办、上线前凭什么说准备好了」**。纯本地单机应用可整体暂缓大部分内容，但依赖清单、离线降级与维护 owner 仍要成文。

不预设：是否有后端、SLO 数值、告警平台、值班制度、供应商。所有具体值由项目决定。

## 开始写代码前，先让 AI 回答这些问题

1. 外部依赖清单：更新服务、API、认证、分析/崩溃监控、支付、CDN、第三方 SDK，各自提供什么、owner 是谁、升级联系人是谁？
2. 每个依赖的服务期望：配额、超时、重试上限、回退行为、失败对用户的可见影响（→《网络与离线弹性技术方案》《客户端与服务端API契约方案》）？
3. 是否测过「依赖本身不可用」而不是只测「客户端处理得对」？关键但不可控的依赖是否构成发布阻断项？
4. 选 2–3 个 SLI（成功率、p95 延迟、数据新鲜度）与对应 SLO？error budget 如何用来裁决「继续发布还是先稳定」？
5. 告警是否只针对**用户可感知症状**？有没有「CPU 80% 就呼人」这类噪声告警（→《性能与资源基线技术方案》）？
6. 每个告警是否有一份 runbook（含义、排查、缓解、升级路径），且从告警负载里能直接点开？
7. 值班轮换、升级联系人、谁有权暂停发布/回滚/切断依赖访问（→《特性开关与远程配置方案》《威胁建模与安全响应方案》）？
8. 应用侧降级：依赖挂了是完整可用 / 只读 / 明确禁用？离线三档如何对齐（→《网络与离线弹性技术方案》）？
9. 上线 go/no-go 评审参加人（研发、安全、支持、值班）、检查项（SLO 已配、runbook 已发、发现项已关、支持已培训、回滚已验、状态页模板）？
10. 依赖变更（SDK 升级、配额调整、区域切换）是否触发重新评审与文书更新（→《遥测与隐私合规方案》《供应链安全与依赖治理方案》）？
11. 门禁结果与版本、提交哈希如何绑定，发布后能否查回「当时绿不绿」（→《CI矩阵与质量门禁方案》《发布交付流水线方案》）？
12. 交接：支持团队影子演练、runbook 走查、长期维护 owner 是谁（→《用户文档与上手支持方案》）？
13. 若当前无后端（主大纲五档「多端/云同步」「账号体系」暂缓），触发重新评估的条件写在哪？

交付给 AI 的设计结果应包含：依赖清单与所有权、失败影响矩阵、SLI/SLO 与 error budget、告警与 runbook、值班与升级、go/no-go 检查表、交接记录。

## 核心纪律

### 一、依赖清单：ownership 比拓扑更重要

| 依赖 | 提供什么 | 技术 owner | 业务/升级联系人 | 配额 | 超时/重试上限 | 回退 | 失败的用户影响 |
|---|---|---|---|---|---|---|---|

- 「谁对这件事负责、出事找谁、已接受什么风险」要能回答；**没有 owner 的依赖是发布阻断项**。
- 依赖行为要实测客户端路径，而不是只信服务方宣称的可用性；关键且不可控的依赖要提前定降级。
- 依赖变更（新 SDK、配额、区域、子处理者）触发重新评审与文书更新（→《遥测与隐私合规方案》《供应链安全与依赖治理方案》）。

### 二、SLO 与告警：只为用户可感知的症状呼人

- 选少量 SLI（请求成功率、p95 延迟、异步管道新鲜度），配 SLO 与 error budget；预算把「发布 vs 稳定」变成数字而非争论。
- 告警按症状（用户操作失败率、更新失败率、崩溃率）而非资源指标（CPU 80%）；值班路由绑定轮换表。
- 每份 runbook 写：告警含义、初步排查步骤、缓解动作、升级路径、需要的日志/关联 ID；从告警负载能直接打开（→《日志与可诊断性技术方案》）。
- 崩溃率、启动失败率与性能指标对齐《崩溃上报与符号还原方案》《性能与资源基线技术方案》，不各定一套阈值。

### 三、降级、门禁与证据

| 依赖状态 | 应用行为 | 用户提示 |
|---|---|---|
| 正常 | 完整功能 | 无 |
| 慢/部分失败 | 超时重试有上限、退避带抖动、缓存/只读 | 就地轻提示（→《操作反馈方案》） |
| 完全不可用 | 离线三档之一：完整可用 / 只读 / 明确禁用 | 明确原因与恢复入口 |
| 数据不一致 | 不假装「实时」，标注陈旧边界（→《统一同步层技术方案》《全局一致性读策略》） | 新鲜度标记 |

- 重试不改语义，幂等键稳定（→《客户端与服务端API契约方案》《原子性提交方案》）。
- 每次推送的门禁结果、依赖版本、SBOM、签名记录按版本存档；清理 CI 运行记录时保留证据（→《CI矩阵与质量门禁方案》《供应链安全与依赖治理方案》）。

### 四、go/no-go 与交接

- 发布评审逐项核销：SLO 已配并观测、runbook 已发布且可点开、渗透/安全发现已关、支持已培训、回滚路径已验证、状态页模板就绪、未验项明确列出。
- 发布说明不得写完成式结论而无行为层证据（→《托盘技术方案》五层验证纪律）。
- 交接：支持工程师影子参与一次调试，runbook 走查，top 3 工单应对准备好，长期维护 owner 点名；**「大家一起维护」等于没人维护**（→《用户文档与上手支持方案》）。
- 事件响应与泄露通知沿用《威胁建模与安全响应方案》的 runbook，避免两套流程矛盾。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 依赖挂了全应用不可用 | 无失败影响矩阵与离线降级 | 逐依赖回退 + 离线三档 |
| 出事不知道找谁 | 依赖无 owner / 升级联系人 | 清单写人 + 值班表 |
| 告警疲劳、真事故被淹没 | 按资源指标告警 | 只告警用户可感知症状 |
| 值班半夜靠 grep 找文档 | 无 runbook 或未挂到告警 | 每告警一 runbook + 告警内链接 |
| 「发布还是稳定」靠吵架 | 无 SLO / error budget | 少量 SLI + 预算裁决 |
| 发布后查不到当时 CI 结果 | 证据未与版本绑定 | 按版本存档 + 清理保留策略 |
| 上线后支持答不上来 | 无影子演练与维护 owner | 交接清单 + 点名 owner |
| 依赖升级悄然改变数据流 | 变更未触发评审 | 变更触发条件 + 文书复审 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 依赖 | 逐依赖模拟不可用/慢/配额超限/返回脏数据，断言降级路径 |
| 告警 | 造一次用户可感知症状，确认告警触发、runbook 可点开、值班路由正确 |
| SLO | 指标采集与误差预算计算可复现；阈值变更有记录 |
| 门禁 | 故意制造一次失败，确认证据按版本可查回 |
| 评审 | 走一遍 go/no-go 检查表，逐项留痕 |
| 交接 | 换一个人只读 runbook 处理一次模拟事故 |
| 发布 | 回滚路径真实演练（→《签名打包与更新分发技术方案》） |

## 给 AI 的实施约束模板

> 先给出外部依赖清单（含技术 owner、升级联系人、配额、超时/重试上限、回退、用户影响）、失败影响矩阵、SLI/SLO 与 error budget、告警与 runbook、值班与升级路径、go/no-go 检查表、证据绑定与交接记录，再写监控接线。**没有 owner 的依赖是发布阻断项；要实测客户端在依赖不可用时的行为，不只信服务方可用性；告警只针对用户可感知症状；每个告警一份可点开的 runbook；SLO 与 error budget 用于发布裁决；门禁结果按版本绑定存档；上线前走 go/no-go 并做支持交接与回滚演练。** 任何「已就绪」「已交接」必须附可观察证据与责任人。当前若无后端，把暂缓理由与触发条件写进立项包并随版本复审。实现后给出依赖故障、告警、门禁、交接的可观察测试，并列出未演练场景。所有 SLO 数值、值班制度、供应商由当前项目需求决定。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 依赖清单与所有权、离线降级的产品决策 |
| 二档 | 失败影响矩阵、超时重试上限、SLO 初值、告警原则 |
| 三档 | runbook、值班路由、门禁证据绑定 |
| 四档 | go/no-go 评审、影子演练、回滚验证、维护 owner 交接——缺项不得发布 |
| 五档 | 按主大纲原暂缓项：无后端/无云同步时可暂缓大部分内容，但依赖清单与触发条件必须保留 |
