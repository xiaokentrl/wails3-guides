# CI 矩阵与质量门禁方案：通用规划方案

## 这份方案是做什么的

来源：主大纲二档「CI 与门禁」整节的四项准入问题（原生 runner 与 CGO 矩阵、基础门禁、E2E 的 `-tags server` 构建、本地重装门禁），以及行业通行的 kickoff / 生产就绪清单（软件发展计划清单「开发环境设置 + 质量门」两节、生产就绪评审中的「依赖所有权与升级联系人」）。

它管**「凭什么说这次提交可以往下走」**：分几层测、每层谁跑、在哪些 OS/架构/CGO 组合上跑、哪一道门红了必须停、证据留在哪里。不管业务测试怎么写（→《Go测试与文件系统模式方案》）、不管交付链的步骤顺序（→《发布交付流水线方案》）、不管发版文本格式（→《版本号方案》）、不管 SBOM 与签名（→《签名打包与更新分发技术方案》）。

不预设：CI 平台、runner 型号、测试框架、覆盖率数值、分支模型。所有具体值由项目决定，未核实的标**待验证**。

## 开始写代码前，先让 AI 回答这些问题

要求先查清锁定的框架版本、目标 OS/架构与现有工作流，给出证据；查不到的标「待验证」，不能把猜测写成结论。

1. 目标平台与架构分别是什么？每个组合是原生 runner、交叉编译还是容器模拟？
2. 是否引入 cgo 依赖（如 SQLite cgo 驱动）？**只有 cgo 依赖才会让 arm64 需要原生 runner 或 Docker**；纯 Go 的 `GOARCH=arm64` 可由原生交叉编译完成，这条要在矩阵里写死，不要凭「跨平台一定要真机」加机器。
3. `CGO_ENABLED` 在每个 job 里的值是多少？依赖清单里哪些包要求 cgo？
4. 测试分几层？每层的入口命令、运行时机（每次 PR / 每日 / 发布前）、失败语义（阻断 / 仅告警）分别是什么？
5. `go test -race ./...` 是否在必需状态检查里？生成器测试是否独立成一个 job？
6. 绑定生成物与源码的 `生成 → git diff --exit-code` 门在哪（→《绑定层契约与生成物方案》）？错误码 parity 门在哪（→《状态码方案》）？
7. E2E 依赖的 `-tags server` 构建是否作为**独立 job 常规执行**？还是等第一次需要 E2E 时才跑？
8. 脚本化 E2E 覆盖哪几条主旅程？flaky 用例的隔离、上限、owner 与复审日期怎么定？
9. 分支保护、必需状态检查、CODEOWNERS、秘密扫描、依赖自动更新（Renovate/Dependabot）是否启用？
10. macOS 签名/公证必须在 Mac runner 完成，凭据配置的从零执行记录在哪（→《签名打包与更新分发技术方案》）？
11. 每次门禁结果如何与版本、提交哈希绑定，供发布时复核「当时 CI 到底绿不绿」（→《发布交付流水线方案》）？
12. 本地推送前的重装门禁是否启用？跳过开关是什么？失败是否中断推送？
13. 哪些门只在发布前跑（签名验证、产物体积、安装冒烟）？它们与 PR 门的边界是什么？

交付给 AI 的设计结果应包含：CI 矩阵表、分层测试表、必需状态检查清单、flaky 治理规则、门禁证据留存方式、失败策略。

## 核心纪律

### 一、分层：五层各有不可替代的判据

| 层 | 抓什么 | 典型入口 | 频率 | 失败语义 |
|---|---|---|---|---|
| 单元 | 领域逻辑、边界条件、纯决策 | `go test ./...` / 前端单测 | 每次 PR | 阻断 |
| 生成器与 CLI | 生成物同步、绑定的模型/方法对账、CLI 冒烟 | `generate → git diff --exit-code`、CLI 冒烟脚本 | 每次 PR | 阻断 |
| `-race` | 并发竞争、goroutine 退出 | `go test -race ./...` | 每次 PR 或每日（写明） | 阻断 |
| 跨平台集成 | 目标 OS/架构构建与启动冒烟 | 矩阵 job | 每次 PR 至少覆盖主平台，全矩阵每日/发布前 | 阻断（目标平台） |
| 脚本化 E2E | 端到端主旅程、安装/升级路径 | `-tags server` + 脚本化驱动 | 每日 + 发布前 | 阻断（发布前） |

「只跑单元测试就发布」与「只靠 E2E 兜底」都是失衡：前者抓不到启动与绑定错配，后者又慢又脆。覆盖率目标按层定，E2E 只覆盖最关键的少数主旅程，不要用 E2E 数量替代金字塔。

### 二、矩阵：按依赖决定机器，不按口号加机器

| 组合 | 纯 Go | 有 cgo 依赖 |
|---|---|---|
| Windows amd64 | 基础构建不需要 CGO；交叉编译或原生 runner 均可 | 需对应工具链的原生 runner |
| Windows/Linux arm64 | `GOARCH=arm64` 原生交叉编译 | 需原生 runner 或 Docker（写明是哪一种） |
| macOS（签名/公证） | 必须 Mac runner | 同左，且凭据配置需从零演练 |
| Linux（Ubuntu 26.04 基线） | 原生 runner；GTK4 + WebKitGTK 6.0 用发行版自带栈 | 同左，不做多发行版兼容矩阵 |

矩阵表里逐格写：`GOOS` / `GOARCH` / `CGO_ENABLED` / runner 类型 / 是否签名 / 产物路径。**「加一台机器」是成本决策，不是安全感的替代品**；反过来，「交叉编译能过」也不等于「在该平台能启动」，启动冒烟必须在目标平台跑。

### 三、门禁：凡是纪律，都要有能红的门

- 静态门：`gofmt` / `go vet`、前端 strict 类型检查、组件库自查脚本、CSS 裸色值/重复导出等库内自查（→《多平台一致组件库方案》）。
- 生成物门：生成后 diff 为空；绑定模型/方法 ID 与源码一致（→《绑定层契约与生成物方案》）。
- 契约门：Go/TS 错误码 parity、配置 Schema 与文档一致（→《状态码方案》《配置文件方案》）。
- 构建门：三平台构建 + `-tags server` 独立 job；E2E 路径常规执行，不能到发布日才第一次编译。
- 发布门：签名与公证凭据、产物版本一致性、安装/升级冒烟、回滚路径（→《签名打包与更新分发技术方案》《发布交付流水线方案》）。
- 权限门：分支保护 + 必需状态检查 + CODEOWNERS + 秘密扫描；**禁止直接 push 到 main 绕过门**（本库自身的 pre-push 重装钩子见《发布交付流水线方案》）。

每条门写清「谁维护、红了怎么办、跳过需要谁批准」。跳过记录要留痕，不能只写在聊天里。

### 四、flaky：重跑是诊断，不是修复

- 任意自动重试有上限，且重试前后都留日志；失败时输出「首次失败 + 重试结果」，不能只留绿的结果。
- 「just rerun, it's flaky」不构成结论：连续 N 次失败即自动隔离，隔离用例必须有 owner、原因与复审截止日。
- 隔离不是垃圾桶：超过复审日仍隔离的用例，在发布评审里作为债列出（与五档「带触发条件的暂缓」同一纪律）。
- 性能/资源类断言用相对阈值与实测记录，别用「本机恰好不超」的绝对数（→《性能与资源基线技术方案》）。

### 五、证据：门禁结果要能追溯到提交

每次推送保留：提交哈希、矩阵逐格结果、生成物 diff、签名/公证记录、产物版本与体积；发布时按版本号能查回这一组证据。没有行为层/构建层记录的，发布说明不得写完成式结论（→《托盘技术方案》「修复之后：怎么证明它真的生效了」的五层验证纪律对本库同样适用）。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 本地全绿、CI 红 | 生成物未提交、依赖版本漂移、`CGO_ENABLED` 默认值不同 | 单一生成命令 + 锁文件 + 矩阵里显式写 CGO 值 |
| arm64 构建偶发失败 | 引入 cgo 依赖却仍用纯交叉编译路径 | 依赖清单标 cgo；矩阵按依赖分档 |
| 发布日 E2E 第一次跑就崩 | `-tags server` 没进常规 job | 独立 job 每次/每日执行 |
| flaky 越来越多 | 无条件重跑，失败原因没人认领 | 重试上限 + 隔离 + owner + 复审日 |
| 改了方法名前端静默错调 | 没有 `generate → diff` 与 parity 门 | 生成物门 + 错误码 parity 门 |
| 公证在 Linux runner 上「跳过」 | 平台约束没写进矩阵 | macOS job 固定 Mac runner + 凭据从零演练记录 |
| 发布后查不到当时 CI 是否绿 | 运行记录被清理/无版本绑定 | 门禁结果与版本、提交哈希绑定存档；清理策略保留最近 N 条 |
| 跳过门禁没人知道 | 跳过不留痕、无批准人 | 跳过记录入库存档并进发布评审 |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| OS/架构 | 目标三平台 × 架构 × CGO 组合；每格至少一次构建 + 启动冒烟 |
| 分层 | 单元 / 生成器与 CLI / `-race` / 跨平台集成 / 脚本化 E2E |
| 生成物 | 生成前后 diff、模型/方法 ID 对账、手工编辑检测 |
| 契约 | 错误码 parity、配置 Schema 与文档、语言键齐性（→《多语言实现方案》） |
| 生命周期 | 首启、隐藏/唤回、退出、升级后从旧快捷方式启动（→《单实例与快速启动方案》《托盘技术方案》） |
| 发布形态 | dev / server / 打包安装；签名、公证、安装与回滚冒烟 |
| 门禁自身 | 故意制造一个失败（改生成物、删一个码映射），确认门真的红 |
| flaky | 重试上限、隔离、复审日的机制测试 |

**最后一行是本方案最容易漏的一条**：门禁本身也要被测。只写工作流不验证「它会不会红」，等于没有门。

## 给 AI 的实施约束模板

> 先盘点仓库里已有的工作流、锁定框架版本、目标 OS/架构与 cgo 依赖清单，给出 CI 矩阵表（逐格写 GOOS/GOARCH/CGO_ENABLED/runner/是否签名）、五层测试表、必需状态检查清单与 flaky 治理规则。**纯 Go 的 arm64 交叉编译不要凭习惯加原生 runner；有 cgo 依赖才需要，且必须写明是哪一种。`-tags server` 构建要作为独立 job 常规执行；生成物、错误码 parity、前端类型检查都要有能红的门；macOS 签名公证固定在 Mac runner。** 门禁用真实命令与失败语义描述，禁止「跑一下测试」这类无判据表述；每个门写清维护人、红了怎么办、跳过需谁批准。实现后用一次故意失败验证门真的会红，并列出未覆盖的平台与形态。所有平台、runner、覆盖率数值由当前项目需求决定，不得从其他项目照抄。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 分层与必需状态检查的基本约定、生成物门的必要性（不回答不写业务代码） |
| 二档 | 完整矩阵、五层门禁、`-tags server` job、本地重装门禁——第一个可分发里程碑前锁定 |
| 三档 | flaky 治理、覆盖率目标按层收敛、门禁自身被测试 |
| 四档 | 发布门（签名/公证/安装回滚）、SBOM 与 CVE 扫描接入、门禁结果与版本绑定存档 |
| 五档 | 性能自动化回归可暂缓（须写理由 + 触发条件）；全架构 E2E 矩阵可按产品覆盖面裁剪并记录 |
