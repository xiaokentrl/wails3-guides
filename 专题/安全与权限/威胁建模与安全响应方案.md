# 威胁建模与安全响应方案：通用规划方案

## 这份方案是做什么的

来源：OWASP Desktop App Security Top 10（DA1–DA10）、DASVS 的分级思想（**待验证**：L1/L2/L3 具体分级来自第三方转述；OWASP 官方 DASVS 页面不可访问，其分级定义自称草案且「不应依赖」，本方案改用项目自定义档位）、行业 kickoff 清单「设计阶段跑一次 STRIDE + 架构评审 + 发布前排期渗透测试」、GDPR 合规清单里的「数据泄露通知与事件响应 runbook」。母法方案：《安全边界与权限技术方案》（信任边界图）、《本地敏感数据与密钥管理方案》（静态数据与密钥）、《外部链接与协议回调安全方案》（不受信 OS 输入）、《登录与权限方案》（认证/授权）、《CI矩阵与质量门禁方案》（SAST/SCA 门）、《日志与可诊断性技术方案》（审计留痕）、《供应链安全与依赖治理方案》（第三方风险）。

它管**「怎么系统性地找出会伤到用户/数据的路径，以及出事之后多久、由谁、做什么」**：威胁建模在设计阶段做、验证分级按风险定、安全测试进 CI、漏洞有响应时限、事件有 runbook 与演练。不管具体加密算法（→《本地敏感数据与密钥管理方案》）、不管业务权限模型（→《登录与权限方案》）。

桌面应用的出发点与普通 Web 不同：**应用跑在用户完全控制的机器上，二进制、内存、本地文件都在攻击面内**。把 Web 侧「服务端可信」的假设搬过来，会漏掉本地提权、二进制篡改、本地数据泄露这几类。

不预设：威胁建模方法论、分级标准、渗透测试供应商、SLA 数值、法规适用范围。所有具体值由项目与安全团队决定。

## 开始写代码前，先让 AI 回答这些问题

1. 系统边界、资产、数据敏感度、参与者分别是什么？数据流图画到哪一层（进程/IPC/磁盘/网络/更新通道）？
2. 信任边界有几处？每处的认证/授权检查点在哪（→《安全边界与权限技术方案》）？
3. 用 STRIDE 六类逐边界走一遍：仿冒、篡改、抵赖、信息泄露、拒绝服务、权限提升，各自最可能的路径是什么？
4. 按资产价值自定义验证档位（建议 T1 低敏 / T2 含 PII 或业务逻辑 / T3 关键基础设施；名称与阈值由项目自定，不引用外部现成分级），选定的理由与由此增加的门是什么？
5. 高风险处理是否需要 DPIA/隐私影响评估（→《遥测与隐私合规方案》）？
6. 威胁建模在设计阶段做完后，哪些变更会触发重做（新增外部接口、新增 SDK、改权限模型、改分发渠道）？
7. SAST / SCA / DAST 分别在哪道 CI 门？桌面 DAST 需要 GUI 自动化与 fuzzing，谁负责（→《CI矩阵与质量门禁方案》）？
8. 预发布渗透测试何时排期（外部测试通常需提前数周预约）？发现项的修复窗口与发布门是什么？
9. 漏洞响应 SLA：按严重度的时限、owner、通知对象、豁免流程？外部漏洞披露渠道与政策是什么？
10. 安全事件 runbook：检测、遏制（谁有权吊销密钥/暂停通道）、范围界定、评估、通知责任、证据保全分别是什么？
11. 若适用 GDPR，72 小时通知监管机构的倒计时由谁启动？「签名密钥泄露但无个人数据暴露」与「支持 dashboard 暴露单用户日志」如何分类？
12. 演练：是否做过桌面特有问题（暴露的支持 token、被攻陷的管理员账号、含崩溃导出的错误配置存储桶、以为匿名实则含标识符的分析导出）？
13. 残余风险谁签字接受？接受记录在哪，复审日期是什么（→《立项范围与决策记录方案》的风险登记）？

交付给 AI 的设计结果应包含：数据流图与信任边界清单、STRIDE 结果表、验证级别结论、安全测试矩阵、漏洞响应 SLA、事件 runbook、演练记录、残余风险登记。

## 核心纪律

### 一、威胁建模在设计阶段，不是上线前补 PDF

| 步骤 | 产出 | 常见错误 |
|---|---|---|
| 定边界 | 系统边界、资产、参与者、敏感度 | 只画前端与后端，漏掉本地文件/IPC/更新通道 |
| 画数据流 | 每箭头标数据类别与信任跨越 | 把「本地存储」当可信 |
| STRIDE 逐格 | 每条路径的威胁、可能性、影响、缓解 | 只列通用漏洞清单，不结合本产品 |
| 定级别 | 自定义档位 + 理由（OWASP 官方分级待验证） | 一律按最高级，成本失控；或一律最低，形同虚设 |
| 落门 | 每个缓解对应一道可红的门 | 缓解只写在文档里 |
| 复审触发 | 变更类型清单 | 建模做完就再不更新 |

**一份有用的威胁模型会记录「选择不收集什么数据」「接受什么残余风险」**，而不是只列防护措施。法务/安全能应对已知风险，应对不了被藏起来的风险。

### 二、桌面特有的攻击面不能漏

| 面 | 例子 | 对应专题 |
|---|---|---|
| 本地数据 | 明文配置、日志带 token、SQLite 未加密 | 《本地敏感数据与密钥管理方案》 |
| 二进制 | 硬编码密钥、DLL 劫持、篡改后仍可运行 | 《供应链安全与依赖治理方案》《签名打包与更新分发技术方案》 |
| IPC / 绑定 | 导出方法默认暴露、高权限 Core 鉴权不足 | 《安全边界与权限技术方案》《绑定层契约与生成物方案》 |
| 外部输入 | deep link 任意路径、文件关联、通知 action | 《外部链接与协议回调安全方案》《输入数据验证方案》 |
| 更新通道 | 未验签更新、回滚路径被利用 | 《签名打包与更新分发技术方案》 |
| 通信 | 关掉证书校验、明文协议、代理不遵循 | 《本地敏感数据与密钥管理方案》《网络与离线弹性技术方案》 |
| 日志与监控 | 无审计留痕、滥用无法发现 | 《日志与可诊断性技术方案》 |

客户端状态一律不可信：本地配置里改布尔值不能提权，UI 隐藏按钮不算鉴权，关键校验在服务端强制（→《登录与权限方案》）。

### 三、验证：自动化 + 人工，各有不可替代的部分

- SAST 抓硬编码凭据、危险模式；SCA 抓已知漏洞依赖；DAST 在桌面需要 GUI 自动化/无障碍 API 与 fuzzing，抓运行时崩溃与输入健壮性（→《CI矩阵与质量门禁方案》《供应链安全与依赖治理方案》）。
- 自动扫描看不懂多步业务逻辑与提权路径，**人工渗透测试必须排期**，且排期对齐 beta 里程碑而非 GA——要留修复窗口。
- 分级决定深度：T1 基础门禁，T2 加深度防御与审计留痕，T3 加对抗性测试与二进制保护评估；每级增加的门写清楚。档位为项目自定义，不宣称等同任何外部标准；**待验证**：若未来引用 OWASP DASVS 官方分级，须核对当期正式发布版本。
- 测试结论按「可观察判据」记录，禁止「已通过安全评审」这种无证据表述（→《托盘技术方案》五层验证纪律）。

### 四、漏洞响应与事件 runbook

| 环节 | 要写死 | 验收证据 |
|---|---|---|
| 接收 | 外部披露渠道、责任人、去重 | 政策页面 + 值班表 |
| 分级 | 严重度定义与对应 SLA 时限 | 分级表 + owner |
| 遏制 | 谁有权吊销 API key、轮换签名凭据、暂停更新通道、切断供应商访问 | 授权名单 + 操作清单 |
| 范围 | 哪些系统可能含受影响个人数据（崩溃日志、支持附件、遥测、发布历史） | 系统映射图 |
| 评估 | 安全事件 / 个人数据泄露 / 两者兼有，由谁判定 | 判定记录模板 |
| 通知 | 监管机构、客户、内部状态更新各由谁负责；适用法规的倒计时 | runbook + 演练记录 |
| 证据 | 清理前必须保留哪些日志、管理事件、访问记录 | 保全清单 |
| 复盘 | 残余风险、门是否要加、复审日 | 风险登记更新 |

**倒计时不等人**：不必等到完全确定才启动流程、保存证据、指定负责人。演练要覆盖「最早信号来自支持/客户成功而非安全团队」的场景。

## 常见根因表

| 表面现象 | 常见根因 | 开始实现前的预防 |
|---|---|---|
| 上线前才补一份威胁模型 PDF | 建模未进设计阶段门 | 架构评审必需产出 + 变更触发重做 |
| 只防 Web 攻击，本地数据全明文 | 把服务端可信假设搬到桌面 | 桌面特有攻击面清单逐格核对 |
| 扫描全绿但业务逻辑被绕过 | 只靠 SAST/SCA，无人工渗透 | 自定义档位 T2+ 排期人工测试 |
| 高危漏洞无人跟进 | 无 SLA、无 owner、无豁免有效期 | 分级时限表 + 值班表 + 复审日 |
| 泄露事件超时才上报 | 没人知道 72h 倒计时由谁启动 | runbook 写死通知责任 + 演练 |
| 演练只测后端故障 | 忽略发布工具/支持导出的隐私事故 | 桌面四类场景逐项演练 |
| 残余风险没人签字 | 接受风险只写在聊天里 | 风险登记（→《立项范围与决策记录方案》） |

## 先设计测试矩阵，再开始实现

| 维度 | 要覆盖 |
|---|---|
| 建模 | 每信任边界的 STRIDE 六格；数据流图与实现一致 |
| 门 | 每个缓解对应一道可红的门，故意违反一次验证 |
| 扫描 | SAST 硬编码凭据、SCA 漏洞依赖、fuzzing 畸形输入/命令行/文件解析器 |
| 人工 | 提权路径、二进制补丁绕过客户端校验、多步业务事务 |
| 事件 | 暴露的支持 token、被攻陷管理员账号、错误配置的存储桶、含标识符的分析导出 |
| 时限 | 从发现到通知责任指派的时间戳演练 |
| 未验 | 未测平台、未测供应商、未做演练的场景明确列出 |

## 给 AI 的实施约束模板

> 先给出数据流图与信任边界清单、STRIDE 结果表、验证级别结论（含理由）、安全测试矩阵、漏洞响应 SLA 与值班表、事件 runbook（检测/遏制/范围/评估/通知/证据保全）、演练记录与残余风险登记，再写安全代码。**威胁建模在设计阶段做，不以上线前补 PDF 代替；桌面应用必须把二进制、内存、本地文件、IPC、更新通道纳入攻击面；客户端状态不作为授权依据；人工渗透测试排期对齐 beta 里程碑；每个缓解对应一道可红的门；事件 runbook 写死通知责任人与倒计时启动人。** 任何「已通过安全评审」「风险已接受」必须附可观察证据与签字人。实现后给出故意失败用例与四类桌面事件演练记录，并列出未测平台。所有分级、SLA 数值、法规适用范围由当前项目与安全/法务决定，查不到依据的写「待验证」。

## 五档定位

| 档位 | 本方案承担 |
|---|---|
| 一档 | 系统边界、资产与数据流图、信任边界清单（不回答不写业务代码） |
| 二档 | STRIDE 结果、验证级别、SAST/SCA 门、漏洞响应 SLA |
| 三档 | fuzzing/DAST、人工渗透排期、事件 runbook 初版 |
| 四档 | 渗透发现关闭、事件演练、披露政策、残余风险签字——缺项不得发布 |
| 五档 | T3 对抗性测试、二进制保护（RASP/白盒密码学）可按资产价值暂缓，须写理由 + 触发条件 |
